# 개발 지속 중단 원인과 보완 (0.4.55)

## 원인
- 이전 두 개발 응답은0.4.53/0.4.54의 한 묶음 구현·테스트 완료 직후 최종 응답으로 끝났다. 최종 응답 이후 실행이 이어지는 구조가 아닌데 작은 작업 완료를 종료 경계로 삼았다.
- AGENTS.md에는 자율 진행 원칙이 있었지만 ‘다음 실행 가능 TODO 선택’과 종료 전 판단 기준이 없었다.
- 마스터 TODO 상단은 완료 이력과 신규 독립 데이터 대기 항목이 중심이었다. 하나의 데이터 의존성을 전체 개발 중단과 혼동할 수 있었다.
- 개발 단계67%는 기능 기반4/6 체크리스트다. 남은 품질 검증이 쉬운2단계라는 뜻이나 정확도67%가 아니다.

## 보완한 실행 규칙
- 구현/테스트 완료는 commentary 중간 성과 공유 후 다음 실행 가능 TODO 처리로 연결한다.
- 사람 정답·새 자료·권한 등에 의존하는 항목만 대기 표시한다. 독립 가능한 코드 보완/진단/검증은 처리한다.
- 종료 전 남은 항목과 실행 가능 여부를 실제로 확인한다. 요청 범위 완료 또는 모든 남은 항목이 실제 외부 의존성에 막힌 경우를 구분한다. 실행 한계가 생기면 체크포인트를 남긴다.
- 억지 기능 추가, 동일 입력 재학습, 완료 라벨 재요청으로 지속을 흉내 내지 않는다.
- 최종 응답 뒤 자동 개발이 이어진다고 약속하지 않는다.
- 에튜는 자기개발에 도움이 되는 기술/설계 개념과 학습 이유로 제시한다.
- 독립 프로젝트 AGENTS.md와 소비 프로젝트 CONDITION_ANALYSIS_TODO.md에 영속 기록했다. 이 규칙이 런타임 스케줄러를 만드는 것은 아니다.

## 실제로 이어서 처리한 코드 보완
사람 개입이 필요 없는 CLI 오류 계약을 재현하고 수정했다.
- 수정 전 실제 `listing-predict`에 손상/빈 checkpoint를 전달하면 exit1이지만 traceback이고 requires_gemini JSON은 없었다.
- 수정 후 pickle.UnpicklingError/EOFError도 공통 CLI 경계에서 짧은 JSON 오류와 requires_gemini=true/exit1을 반환한다.
- torch.load(weights_only=True)는 유지하고 안전하지 않은 pickle 재로딩을 시도하지 않는다.
- 이것은 호출자가 보류를 처리할 수 있는 오류 계약 보완이며 Gemini 실제 호출을 구현하거나 모델 정확도를 개선한 변경이 아니다.

## 현재 의존성 점검
이번 보완까지 승인된 상단 실행 항목을 처리했다. 상단 미완료 독립 최종평가는 새 실물 자료가 필요하며 사용자 답변 ‘새 사진 없음’을 유지한다. 기존 train/val을 test로 바꾸거나 사진을 반복 요청하지 않는다. 운영 채택은 독립 검증과 별도 소비 서비스 단계가 필요하다. 새로운 코드 문제를 확인하면 사람 판단 없이 해결 가능한 범위는 계속 처리하되, 근거 없는 추가 기능을 만들지는 않는다.

## 리스크 / 롤백
CLI 오류 JSON이 이전 traceback 대신 나오므로 traceback 문자열에 의존하던 외부 도구가 있다면 동작이 달라질 수 있다. Python API는 기존 예외를 그대로 전달한다. 모든 가능한 손상 파일 형태를 포괄한다고 주장하지 않으며 새 예외가 재현되면 별도 검증한다.
`.backups/human-loop-0455`의 AGENTS.md/cli.py/pyproject.toml/README.md를 원래 위치로 복원하고 신규 tests/test_cli_checkpoint_error.py만 제거하면 코드/지침 롤백된다.0.4.54 wheel을 사용할 수 있다. 소비 TODO의 해당 규칙·항목도 필요할 때 따로 복원한다. 모델/라벨은 변경하지 않았다.

에튜: Blocking Dependency(선행 의존성)를 작업별로 구분하는 법을 익히면 한 데이터가 없어도 전체 개발을 멈추지 않고, 독립적으로 할 수 있는 일을 찾아 진행할 수 있다.
