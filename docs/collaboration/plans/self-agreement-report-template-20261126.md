### 1.5 도구 출력에 없는 것

아래는 `result.json`에 열쇠가 없다(`SR:74-95`). "도구 출력 없음"으로 적고, 따로 확인한 기록이 있으면 출처를 달아 구분한다.

- 판정 주체 확인 문장 원문과 확인 성공 표시(문제가 있으면 `reasons`에만 "주체 미확인" 표시, `decide.py`의 `invalid`).
- 제출 시각과 실제 간격 시간(이탈은 `reasons`에만).
- 기준 문구 버전, 기준·화면·크롭 해시 값(불일치는 `reasons`에만). `QUALITY_RULES.md:24`의 버전별 분모는 별도 근거가 필요하며 없으면 "버전 미상".
- 값 쏠림 비율의 별도 열쇠(쏠림일 때 `reasons` 문자열에만, `decide.py:44-51`).
- 3분류 카파의 구간.
- 12절의 세 장수.
- b+c ≤ 5라 방향 검정이 3행 문턱에 닿을 수 없다는 표시(`P:123`).

**원문과 도구의 차이**: `P:123`은 2행이 방향 쏠림을 가릴 수 있으므로 보고에 b+c를 함께 적으라고 한다. 도구는 1·2행에서 `b`·`c`·`table`을 `null`로 낸다(`SR:70,79-84`). 이 틀은 손계산을 넣지 않고 "b+c: 도구 출력 없음(`P:123`과의 차이)"이라고 적는다. **[틀]** 바꾸려면 2차 점수를 계산하기 전에 사용자가 정해야 한다.

## 5. 판별 가능성의 세 장수 갱신

근거 규칙: `can-this-experiment-tell`(`QUALITY_RULES.md:87-91`). 시작 값은 `P:192-194`다. 도구는 이 세 수를 내지 않는다. 보고서에는 행과 상관없이 세 줄을 모두 적는다.

| 수 | 결과로 갱신하는 법 |
|---|---|
| ① 겨냥 묶음 장수 | **바꾸지 않는다.** 0, 입력 경로 진단에 한정. 다른 가설에서는 미측정(`P:192`). 이 측정은 라벨 진단이라 오류 원인을 새로 분류하지 않는다(`P:188`) |
| ② 필요 개선 | **바꾸지 않는다.** 오탐 9→7, 2장(카드). 인용 원본 표 미확인 한정도 유지(`P:193`) |
| ③ 라벨 흔들림 | 아래 행별 표. 단위는 **구역**, 층은 **주 층만** |

| 행 | ③에 적는 값 |
|---|---|
| 1 | 미측정(정식 값 없음) |
| 2 | 미측정 |
| 3 | 미측정. 불일치는 1.3에만 적는다. **[틀: `P`에 3행의 ③ 처리 규정이 없어 보수적으로 정함]** |
| 4·5·6 | "주 층 구역 불일치 `<b+c>`/`<counts.confirmed_pairs>`(구역, 자기 일치, 한계 H1~H9)". 카드 환산은 미측정. **[틀: `P:157`은 5행에서 다시 쓰라고만 하며 4·6행도 같은 형식으로 정함]** |

- ②는 카드, ③은 구역이다. 환산법이 없으므로 **②와 ③의 대소 비교를 하지 않는다**(`P:145,196`). ③에 값이 생겨도 `QUALITY_RULES.md:89`의 "②가 ③보다 작으면" 판단은 할 수 없다고 적는다.
- **③은 오탐 층 `flips`로 채우지 않는다.** 모델이 틀렸다고 본 카드를 골라 잰 값이므로 참고로만 적는다(`P:197`). 오탐 층 구역 b+c도 ③에 넣지 않는다(`P:81,166`).
- 확정 쌍 수는 구역 분모다. 위 불일치 건수를 전체 구역이나 다른 평가의 장수로 곱해 옮기지 않는다(`P:112,168`).
- 미측정을 0으로 치지 않는다(`QUALITY_RULES.md:91`).

## 6. HTML 보고

HTML 의무는 두 가지이고 따로 판단한다.

| 의무 | 점수 결과를 보고할 때 | 이유 |
|---|---|---|
| 사진 위 구역별 사람 정답·모델 출력 비교 HTML(`AGENTS.md:55`, `HTML_REPORTING.md:9`) | **해당 없음** | 모델 성능을 새로 평가·비교하지 않고 새 추론이 없다. 같은 판정자의 두 답을 비교하는 라벨 진단이다(`P:188`). 정확도·누락·오탐 개선 그래프도 만들지 않는다 |
| 성과·진척 HTML(`AGENTS.md:89`, `HTML_REPORTING.md:5-7`) | **필요** | 원문은 새 평가 여부와 상관없이 "개발 묶음의 중간 성과/최종 인계 시" 생성·갱신하고 열라고 한다(`HTML_REPORTING.md:5`) |

성과·진척 HTML에 적용할 것:

- 첫 화면에 작업명·검증 코드 SHA·개발 진척률·이번 성과를 둔다. 진척률은 `PROGRESS_CRITERIA.md`와 `development-progress.json`을 읽어 고정 기준과 버전·근거를 적고, 일치율과 섞지 않는다(`HTML_REPORTING.md:6`).
- 변경 파일·핵심 diff·실제 검사·미실행 검사·남은 의존·리스크·롤백·근거 파일을 적는다(`HTML_REPORTING.md:7`). 모델 학습·추론이 없었음을 밝힌다.
- 이 틀의 1~5절 문장 규칙을 그대로 따른다.
- 실자료 HTML은 Git 제외 `artifacts/`에 두고 외부 CDN·API 없이 만든다. 원본 사진·사람 응답·비밀값·홈 절대경로를 Git에 넣지 않는다(`HTML_REPORTING.md:10`).
- 정확한 산출물 경로는 채점·보고 task 계약에서 지정하고 생성·내용 대조·열기를 checks·handoff에 넣는다(`HTML_REPORTING.md:11`, `PAIR_CODING.md:126`). 열기 요청 성공과 렌더 확인을 구분해 적는다(`HTML_REPORTING.md:13`).

이 틀을 작성한 작업: 점수·실행 성과가 없는 문서 준비라 `HTML_REPORTING.md:5`의 "지침/프롬프트 준비만 하는 턴은 실행 성과를 만들지 않는다"에 해당한다고 **해석**해 HTML을 만들지 않았다. 남는 긴장: `AGENTS.md:89`·`HTML_REPORTING.md:11`·`PAIR_CODING.md:126`은 새 task 계약에 HTML 경로를 넣으라고 하는데, 이 작업의 허용 파일은 이 문서 하나이고 HTML 경로가 없었다.
