## B. 가져옴 상세

### B-1. test-collaboration — 고친 결함은 실제 실패 모양으로 회귀 검사를 남긴다

- 출처 표기: frontmatter에 origin·license 없음 → **"표기 없음"**. 아이디어만 다시 쓴다.
- 관점: 1·3
- 원문 근거: 103~112줄. 인용 "The TEST-ID must reproduce the real failure shape rather than an easier similar input." 같은 절에서 "고치기 전 실패와 고친 뒤 성공을 기록한다", "검사 ID나 명시적 수동 종료가 없으면 결함은 닫히지 않은 것이다"라고 한다(요약).
- 우리 현재 방식:
  - 모델 오류: README 4절의 "추가한 회귀 평가" 칸이 확인한 오류를 `required_cohorts`에 넣었는지, 안 넣었으면 왜인지 적게 한다(README.md:73). 실행기가 그 평가를 동결한다(COMMON_EXPERIMENT_RECORDS.md:62~80).
  - 라벨 안내 문구 결함: "화이트닝은 정상"이라는 잘못된 문구가 여러 번 다시 나왔다(LABELING_PROTOCOL.md:44~45, 보고서 §59·§62·§97). 그런데 tests/에는 `label_instructions`나 `SURFACE_INSTRUCTIONS`를 참조하는 검사가 없다(grep 0건). 모서리 화면 검사(tests/test_mobile_corner_label_pages.py:31~38)는 들어가야 할 문구만 확인하고, 다시 나오면 안 되는 옛 문구는 확인하지 않는다.
  - AI 판정 지시서 결함: v2는 특정 실패 사례(`ebay-pair-82a2671a60bdb9` 호 위 흰 흔적을 정상으로 판정) 때문에 고쳤다(CORNER_JUDGE_PROMPT_STRICT_20261123.md:3). 그런데 "개정 효과는 미검증"이고(같은 파일:61), 그 사례를 고정 회귀 항목으로 다시 돌렸다는 기록은 찾지 못했다.
- 원문이 더 나은 점: 원문은 회귀 장치를 모델 출력뿐 아니라 고친 결함 전체에 걸고, 결함이 닫혔다고 하려면 증거를 요구한다. 그 증거는 실제 입력으로 고치기 전 실패와 고친 뒤 통과를 보이는 것이다. 우리는 이 장치가 모델에만 있다. 그래서 라벨 화면 문구와 AI 판정 지시서는 같은 결함이 다시 들어와도 알아챌 방법이 없고, 실제로 문구 결함이 다시 나왔다.
- **우리 것으로 만든 규칙 초안**:
  1. 라벨 화면 안내·AI 판정 지시서·worker에서 확인된 결함을 고치면, 실제로 문제가 된 입력(잘못된 문구 원문, 놓친 구역 ID와 원본 크롭)을 그대로 쓰는 회귀 검사를 함께 남긴다. 비슷하지만 더 쉬운 입력으로 바꾸지 않는다.
  2. 자동 검사가 불가능하면(예: AI 판정은 실제 모델 호출이 필요함) "수동 확인 절차·마지막 확인 날짜·미확인 사유"를 적는다. 둘 다 없으면 그 결함은 "미해결"로 보고한다.
  3. AI 판정 지시서를 바꾼 이유가 된 사례는 지시서 옆 회귀 목록에 고정한다. 다음 판정 보정(사람 라벨 대조)에서 그 사례의 고치기 전과 고친 뒤 판정을 따로 보고한다. 회귀 목록 사례는 보정 분모와 섞지 않는다(내 응용: 모델 결과로 고른 사례라 치우치기 때문).
- 넣을 자리: README 4절 "추가한 회귀 평가" 칸의 범위를 "모델 오류 → required_cohorts"에서 "라벨 화면·판정 지시서·worker 결함 → 회귀 검사 또는 수동 종료"까지 넓힌다. 지시서 쪽은 CORNER_JUDGE_PROMPT_STRICT 8절(완료 원칙) 끝에 회귀 목록 한 줄을 넣는다.
- 효과를 확인하는 방법: 같은 결함이 다시 나온 횟수(예: 화이트닝 문구처럼 정정 뒤 재발한 건수)를 정정 기록에서 센다. 지시서 개정 사례의 고치기 전 판정과 고친 뒤 판정이 실제로 갈렸는지 본다. 재발이 원래 드물어서 짧은 기간으로는 효과를 재기 어렵다.
- 확신도: **중간**. 반대 근거: AI 판정 회귀는 실제 모델 호출이 있어야 해서, 호출 금지 개발 턴에서는 수동 종료 기록만 쌓이고 실제 검증이 늦어질 수 있다.

### B-2. returns-reverse-logistics — 재감사 일치율에 목표선·경고선을 미리 고정한다

- 출처 표기: origin ECC, **license Apache-2.0**(파일 frontmatter 4줄). 아이디어만 다시 쓴다. 원문 문장은 옮기지 않는다.
- 관점: 2·3
- 원문 근거: 219~222줄(성과 지표 표). 인용 "Inspection accuracy (grade agreement on audit) | > 95% | < 88%". 59줄은 검사 속도와 정확도가 서로 당긴다고 짚는다(30초 육안 검사는 외관 결함을 놓친다).
- 우리 현재 방식: 같은 사람 재판정을 연구마다 따로 설계하고 재측정한다(w1-label-ceiling-20261123.md:6~17, w1-blind-rejudge 계획의 kappa 보고 방식). 판정 규칙은 "분모 <30이면 미측정", "상한 ≤ AUC+0.03이면 보류"뿐이다(w1-label-ceiling-20261123.md:30~33). 칸별 일치율에 상시 목표선·경고선은 없다(PROGRESS_CRITERIA·AGENTS·plans에서 kappa 문턱을 grep했으나 찾지 못함). 라벨 화면의 결함 수준 문구는 최근 바뀌었다(LABELING_PROTOCOL.md:64~71).
- 원문이 더 나은 점: 원문은 재감사 일치율을 매번 보는 운영 지표로 두고, 목표와 경고선을 미리 숫자로 정한다. 그래서 기준이 흐려진 것을 따로 연구를 기획하기 전에 경고선에서 잡는다. 우리는 재판정이 사건이 터질 때만 열려서, 기준 문구가 바뀐 뒤의 흔들림을 다음 연구 전까지 모른다.
- **우리 것으로 만든 규칙 초안**:
  1. 칸(표면·엣지·모서리·관찰 제한)마다 같은 사람 재판정 일치율의 목표선과 경고선을 결과를 보기 전에 정해 문서에 고정한다. 판정 단위는 그 칸의 기존 단위를 따르고, 분모가 30 미만이면 "미측정"이다.
  2. 경고선 미만인 칸은 그 칸 라벨로 새 모델 가설을 내기 전에 기준 문구와 제시 방식부터 점검한다(README 1절 "라벨 쪽" 묶음으로 보낸다). 새 라벨 화면 문구가 바뀌면 그 칸의 일치율을 다시 재야 할 대상으로 표시한다(A3의 기준 문구 버전과 짝).
  3. 재측정용 재판정 구역을 새 라벨 묶음에 섞는 것은 완료 라벨 재요청이므로, 비율과 장수를 정해 사용자 승인을 받은 뒤에만 한다(내 응용: 원문은 감사를 어떻게 하는지 정하지 않는다).
- 넣을 자리: LABELING_PROTOCOL.md 끝에 "라벨 일치도 관리" 절을 새로 둔다. 숫자는 사용자 승인으로 정한다. 원문의 95%·88%는 반품 검사 분야 값이라 옮기지 않는다.
- 효과를 확인하는 방법: 문구 개정(예: 2026-11-24 결함 수준 문구) 전후의 칸별 일치율과 분모를 나란히 보고, 경고선이 실제로 모델 가설 대신 문구 점검을 이끌어 낸 횟수를 센다. 모서리처럼 분모가 모자란 칸은 당분간 측정하기 어렵다.
- 확신도: **낮음~중간**. 반대 근거: 지금도 모서리 구역 단위 사람 재판정 분모가 4라서 경고선을 계산할 수 없고, 상시 재판정은 사람 시간을 쓴다. 사람 시간은 지금 가장 큰 병목이다.

## C. 보류 메모

- pytorch-patterns: README 3절 점검표에 "특징 추출·평가 경로가 eval 모드와 no_grad/inference_mode인가"를 9번째 줄로 넣을 만하다. 새 worker가 이를 빠뜨리면 캐시 특징이 배치 구성에 따라 달라진다. 지금 코드는 이미 지키고 있어 우선순위가 낮다.
- santa-method: 두 판정이 엇갈린 구역을 지시서 기준 항목별(A-3 흰 점, A-4 직선 변 제외, A-6 경계)로 세어 "불일치가 몰린 기준 = 문구를 좁힐 기준"으로 쓰는 진단(295줄). A2를 적용할 때 덧붙이면 된다.
- skill-comply: 규칙 감사에 "사용자 요청이 규칙과 부딪히는 상황"을 한 가지 넣는 발상(61~63줄). 스킬 선택표 세션 감사를 다시 할 때 참고한다.
