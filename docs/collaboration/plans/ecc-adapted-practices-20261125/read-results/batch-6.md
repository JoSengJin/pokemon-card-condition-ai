## B. 후보 상세

### 1. osint-investigation
- origin: "Adapted from shoyann/RZK-The-Hunter", license: **CC-BY-SA-4.0** (ECC MIT 아님). 문장 복사 없이 아이디어만 각색해야 한다.
- 관점: 1, 3
- 근거 구간:
  - 94–125줄 (원본 큐와 가설 장부 분리, "hypothesis debt", 막힌 원본 ≠ 반증된 가설)
  - 127–152줄 (가설을 키우기 전에 가장 싼 반증을 먼저 실행, 결론 안 난 결과는 확정도 기각도 아님)
  - 154–160줄 인용: "Rewording a query, changing tools, or finding another copy is not progress."
  - 190–194줄 (한 원본에서 나온 복사본 셋은 계보 하나)
- 채우는 빈자리: 이미 갖춘 "오류 원인 분해 보고서"는 일회성이고, 우연 판별 도구는 실험 결과를 사후에 본다. 남은 오류 14장과 미채택 변형 3개에 대해 **오류마다 계속 갱신하는 가설 장부**(주장 / 가장 강한 반대 근거 / 가장 싼 반증 / 상태: 열림·유력·반박됨·확인됨 / 막힘 사유)는 없다. "새 근거가 바뀌지 않았으면 진척이 아니다"라는 기준도 같은 자료 반복 실험(얻어걸린 향상 금지)을 실험 *전에* 거르는 규칙이 된다. 190–194줄의 계보 개념은 AI 판정자 2회 독립 판정에 바로 쓸 수 있다. 같은 모델·같은 크롭으로 두 번 돌린 판정은 독립된 확인 두 개가 아니라 계보 하나로 세야 하므로, AI 일치를 사람 라벨의 뒷받침으로 쓸 때 과대평가를 막는다.
- 각색 방법: 오류 14장 각각에 "가설 / 가장 강한 반대 근거 / 가장 싼 반증 (예: 홀더 사진 3장만 크롭 재추출 후 확률 변화 보기) / 상태"를 적는 표 한 장을 두고, 새 실험 계획에는 "어느 가설의 반증인가"와 "이전 시도와 다른 근거원·표현(원본 사진, 다른 해상도, 다른 면)인가"를 필수 칸으로 넣는다. AI 판정 집계에는 계보 칸(모델·프롬프트·입력 크롭)을 붙이고 같은 계보는 1표로 센다.
- 확신도: 중간. 반대 근거: OSINT 지리 추정용이라 대부분(6절 장면·기하 검증)은 카드와 무관하고, 장부 유지 비용이 실험 하나보다 클 수 있다.

### 2. operator-approval-loop
- origin·license: 표기 없음 (frontmatter에 metadata 없음)
- 관점: 2, 3 (라벨 잡음·kappa)
- 근거 구간: 40–50줄 (초안 해시와 epoch 회전), 83–89줄 인용: "A decision whose epoch does not match the current `updated_at` is stale". 91–98줄 (승인 시점 텍스트·해시 불변 스냅샷, 현재 내용으로 과거 승인을 소급 채우지 않음)
- 채우는 빈자리: 이 스킬의 메시지 발송 장치는 무관하다. 다만 "승인은 그때 본 정확한 내용의 해시에 묶이고, 내용이 바뀌면 옛 승인은 새 내용에 적용되지 않는다"는 원칙을 사람 라벨에 옮길 수 있다. 라벨 페이지의 크롭·안내 문구(예: 결함 수준 기준 문구 추가)·확대 방식이 바뀌면 같은 구역 라벨이라도 다른 기준으로 받은 라벨이 된다. 각 라벨에 "그때 보여준 크롭 이미지 해시 + 페이지/기준 문구 버전"을 붙이면, 재판정 kappa 0.47~0.62가 사람 흔들림 때문인지 기준이 바뀐 탓인지 나눌 수 있고 기준 버전이 섞인 라벨을 같은 분모로 비교하는 일을 막는다. 미리 채우기 격리나 답 판정 주체 기록(사람/AI)과는 축이 다르다. 그 둘은 *누가·어떤 영향 아래* 답했는지를 기록하고, 이 아이디어는 *무엇을 보고* 답했는지를 기록한다.
- 각색 방법: 라벨 저장 형식에 `shown_crop_sha256`, `page_criteria_version` 두 칸을 추가하는 규칙을 둔다. 소급해서 채우지 않고 과거 라벨은 "버전 미상"으로 남긴다. kappa·누락률을 보고할 때 기준 버전별로 분모를 나눠 적는다.
- 확신도: 중간. 반대 근거: 프로젝트가 이미 페이지 버전을 기록하고 있을 수 있다(확인 안 함). 과거 라벨은 버전 미상이라 당장 분석할 표본이 작다.

### 3. orch-pipeline
- origin: ECC, license: 표기 없음
- 관점: 4
- 근거 구간: 39–54줄 (세 신호 중 가장 높은 등급으로 크기 판정). 인용: "state the result in one line so the user can override". 25–31줄 (작업 종류별 첫 행동: fix=실패 재현 먼저, tweak=테스트를 새 명세로 먼저 수정)
- 채우는 빈자리: (비공개). Superpowers brainstorming은 열린 질문을 던지는 절차라 짧은 요청마다 쓰기엔 무겁다. 여기서 가져올 것은 질문 없이 "종류·크기·첫 행동"만 선언하는 가벼운 형식이다.
- 각색 방법: 작업 시작 응답 첫 줄 양식을 정한다. "[결함 수정 / 동작 변경 / 새 기능 / 구조 정리 / 조사·설명] · [작음 / 보통 / 큼] · 첫 행동: … · 손대지 않을 것: …". 예: "결함 수정·작음·첫 행동: 누락 5장 재현 목록부터, 모델 파일은 안 건드림". 사용자가 그 줄만 보고 방향을 고칠 수 있게 한다.
- 확신도: 낮음. 반대 근거: (비공개).
