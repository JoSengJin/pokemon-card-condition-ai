# 모델·Effort·토큰 최적화 정책 (model-routing-design)

작성 2026-11-27, Claude. 같은 날 사용자가 아래 1절 정책을 **자율 개발 하네스의 초기 운영 정책(`routing-policy-v1`)으로 승인**했다. 이 문서는 새 학습·추론·외부 AI 호출·라벨 요청의 승인이 아니며, 기존 승인·잠금·소유 파일 규칙(`AGENTS.md`, `PAIR_CODING.md`, `docs/agent/HARNESS_RULES.md`)이 우선한다. 하네스 설계 14절과 DECISIONS D-4가 이 문서를 가리킨다. 구현 시점은 IMPLEMENTATION 3~4단계다.

이 정책은 하네스가 **실행 중에** 작업별 모델을 고르는 정책이다. 하네스를 **만드는** 개발 세션의 모델 배정(IMPLEMENTATION 5절)과는 별개다.

## 1. 승인된 정책 `routing-policy-v1` (사용자 승인 2026-11-27)

### 1-1. 작업 유형별 라우팅

| 작업 | 모델 | Effort |
|---|---|---|
| 일반 개발 및 코드 수정 | Sonnet | Medium |
| 복잡한 알고리즘 구현 | Sonnet | High |
| 일반 카드 이미지 분석 | Sonnet | Medium |
| 자동 Silver 라벨링 | Sonnet | Medium |
| 정밀 결함 분석 | Sonnet | High |
| 독립 라벨 교차 검증 | Sonnet | High |
| 라벨 불일치 분석 | Opus | High |
| 일반 오분석 원인 분석 | Sonnet | Medium |
| 반복 개선 실패 원인 분석 | Opus | High |
| 복잡한 모델 구조 재설계 | Opus | High |
| 실험 로그 요약 | Haiku | Low |
| 학습·추론·평가·통계·파일 처리·상태 관리·한도 대기 | LLM 미사용 | 해당 없음 |

### 1-2. 모델 상향

- 기본은 작업에 필요한 최소 모델과 Effort다.
- 복잡성 증가, 품질 관문 미달, 검증 실패, 해결되지 않는 불일치가 있으면 상향한다.
- 일반 순서: Sonnet Medium → Sonnet High → Opus High.
- 모든 실패에 기계적으로 상향하지 않는다. 데이터 부족, 이미지 품질, 코드 오류 등 원인을 먼저 구분한다.
- Opus Xhigh는 복잡한 구조적 문제에서 필요성이 확인된 경우에만, 예산 범위 안에서 쓴다.
- 상향 모델로도 판단할 수 없는 라벨은 Pending으로 처리하고, 학습 가치가 높은 경우에만 사용자에게 요청한다.

### 1-3. 이미지 분석·자동 라벨링

- 일반 Silver 라벨링은 Sonnet Medium. 미세 결함·판단이 어려운 이미지는 Sonnet High.
- 불확실한 사례는 독립 검증 에이전트 또는 결정론적 CV 분석으로 교차 검증한다.
- 해결되지 않는 불일치는 Opus High로 재분석한다.
- 복수 에이전트의 합의 자체를 정확성의 증거로 쓰지 않는다. 자동 라벨링 품질은 Gold 보정 표본으로 검증한다.
- 기존 검증 결과를 재사용할 수 있으면 비전 호출을 반복하지 않는다.

### 1-4. `route()` 연계

- 입력: 작업 계약의 `task_type`, `needs_llm`, `needs_vision`, `risk`, 맥락 크기, 예산, 이전 실패 결과.
- `needs_llm=false`이면 모델을 호출하지 않는다.
- 정책은 실행 코드와 분리해 변경할 수 있게 한다(정책 데이터 파일 + 판본).
- 설치 환경에서 모델·Effort 지정이 지원되는지 확인한다. 지원되지 않는 설정은 조용히 무시하지 않고 **실제 적용값과 제한 사항을 기록**한다.
- 정책이 없으면 하네스 설계의 기본값을 쓰고 `policy=none`으로 기록한다.

### 1-5. 토큰 최적화

- 결정론적으로 처리할 수 있는 작업에는 LLM을 쓰지 않는다.
- 같은 이미지·분석 영역·라벨 기준 판본·프롬프트 판본·모델·Effort의 유효한 분석 결과를 재사용한다.
- 불필요한 전체 컨텍스트를 넘기지 않는다. 상향할 때는 해당 작업에 필요한 근거와 실패 결과만 넘긴다.
- 사용량 한도가 소진되면 기존 Supervisor 복구 정책(DESIGN 12절)을 따른다.

### 1-6. 정책 검증 기록

가능한 범위에서 장부에 남긴다: 정책 판본, 작업 유형, 요청·실제 적용 모델·Effort, 상향 이유, 토큰 사용량, 실행 시간, 품질 관문 결과, 재작업 여부. 정책 최적화의 근거는 실제 Gold 표본의 라벨 정확도, 최종 모델 성능 개선, 토큰 사용량, 재작업 비용이다. **이 정책의 정확도·토큰 절감 효과는 아직 측정되지 않았다.**

## 2. 구현 연계 메모 (구현 단계에서 확인, 새 요구 아님)

- T7 통과 조건: 장부의 요청값·실제 적용값이 정책 판본과 일치하고, 지원되지 않은 설정은 제한 사항으로 기록되어 있어야 한다. 실제 적용 여부를 확인하기 전에는 통과 처리하지 않는다.
- 정책 표에 없는 `task_type`은 추정하지 않고 `policy=none` 기본값 경로로 처리하고 기록한다.
- 위 1-2의 "원인 먼저 구분"은 장부의 `failure_kind`(transient/deterministic)와 실패 서명을 입력으로 쓴다. 원인 분류가 없으면 상향하지 않는다.

## 3. 설계에서 정해진 것 (토큰·리소스 최적화, 원문 §10 요지, 2026-11-27 이전 기록)

- 파일 처리·데이터 집계·지표 계산·상태 관리·대기는 결정론 코드가 맡는다. LLM은 원인 해석과 설계에만 쓴다.
- Claude에게는 전체 로그 대신 `artifacts/development-cycle/latest.json`, 대표 실패 사례, 핵심 지표만 읽힌다.
- 다중 에이전트는 정확도 향상이 입증되기 전까지 쓰지 않는다. 의견 일치나 자체 신뢰도는 정확도 증거가 아니다(기존 규칙).
- GPU·CPU·메모리·디스크·실험 횟수·사용량 예산 수치는 미설계.

## 4. 이미지 분석·자동 라벨링 기존 기록 (원문 §6 요지)

- 정량화 가능한 항목은 검증된 CV 알고리즘을 우선한다(센터링은 현재 미지원).
- 에이전트의 "보임/안 보임"은 사람 라벨이 아니다(`docs/agent/QUALITY_RULES.md:83`). AI 라벨은 Silver로 분리하며 Gold로 승격하지 않는다.

## 5. 확인된 실행 수단 (사실, 설치본 `claude` 2.1.310 `--help` 기준)

- `--model`, `--effort <level>`, `--fallback-model`, `--max-budget-usd`(`--print` 전용), `-p/--print`, `--bg`, `--resume` 옵션이 있다. 실제 값 지원 범위(예: Haiku·Xhigh)는 3~4단계에서 실행해 확인한다(미확인).
- 세션 중 모델·effort 변경 도구가 있다(`set_session_model`, `set_session_effort`). 하네스는 쓰지 않고 `claude -p --model --effort`로 작업마다 지정한다.
- `/rate-limit-options`는 공식 문서에서 확인하지 못했다(미확인). 자동으로 쓰지 않는다.
