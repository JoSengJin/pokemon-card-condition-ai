## 확정된 사용 방향과 남은 선택

사용자 요청: **“카드 검토는 모바일 앱 원격에서 하고싶어”**. 따라서 PC 브라우저를 사용 화면으로 만들자는 이전 제안은 모바일 원격 앱 경로로 대체한다. 휴대폰 앱에서 사진 입력·결과 확인·사람 검토 기록을 수행한다. AI 분석은 원격 분석 서비스가 맡는 안으로 준비한다. PokeCollector 연결/독립 CLI 소비경로 인정으로 해석하지 않는다.

사용자가 **“안드로이드야 원격pc는 계속 실행중”**이라고 답해, **안드로이드 설치 앱 + 현재 계속 실행 중인 PC의 분석 서비스**로 확정했다. 휴대폰 종류/상시 PC 여부를 다시 묻지 않는다. “모바일 앱”을 모바일 웹/PWA로 임의 대체하거나 이미 구현·접속 가능한 앱으로 표현하지 않는다.

F2 기준안 방향 질문은 별개로 남아 있다. 현행 F2는 앞뒤 쌍/손상 판정을 요구하고 모델은 후면 점검 순위만 제공하므로, 후면 보조용 구체 기준안을 제시해 검토받거나 현행 완료 판정을 보류해야 한다. 모바일 원격 사용 선택 자체는 F2 기준 개정/시범 시작 승인이 아니다.

## 모바일 원격 사용 흐름 (방향 확정, 구현 전)

`휴대폰 앱 → 후면 사진 촬영/선택 → 실물 ID 지정/기존 ID 선택 → 카드 영역 확인 → 원격 분석 요청 → 고정 릴리스의 지원 4칸 결과 수신 → 앱 사진 위 구역/우선순위 확인 → 사람 판단·보류/수정·시간 기록`

- 안드로이드 앱은 사진을 보내고 결과를 보여주는 검토 화면이고, 현재 계속 실행 중인 PC가 AI 분석을 맡는다. 별도 클라우드 서버를 첫 경로로 추가하지 않는다. PC 실행 중이라는 답변은 원격 통신/접속 설정이 이미 검증됐다는 뜻은 아니다.
- 같은 Wi-Fi 안에서만 되는 화면을 집 밖에서도 되는 원격 경로로 간주하지 않는다. 실제 사용할 접속 범위를 확인하고 휴대폰→허용된 원격 연결→분석 호스트→휴대폰 결과 표시까지 검증한다. 이번에 서버/공개 포트/외부 터널/원격 계정을 만들거나 열지 않았다.
- 허용된 사용자만 요청·결과에 접근하도록 하고 사진 전송을 보호한다. 연결 방법은 플랫폼/호스트가 정해진 뒤 구현 계약에서 고정한다. 접속 주소·키·사진을 공개 문서/usage 로그에 넣지 않는다.
- 실물 ID와 요청 ID는 다르다. 같은 카드 재확인과 끊긴 요청 재전송을 구분한다. 재연결/앱 재시작 뒤 중복 접수·중복 저장·다른 사진에 결과 표시가 없는지 F1에서 확인한다. 실물 수는 사람이 확인한 실물 ID로 센다.
- 후면 엣지·모서리·표면 점검 순위와 관찰 제한 재촬영 참고 점수만 표시한다. 손상/정상 확정·전체 완료로 바꾸지 않는다. 앞면·센터링은 미지원/사람 검토다.
- PC 꺼짐/통신 끊김/사진 전송 실패/앱 중단/서버 실패/전부 보류이면 앱에서 같은 사진을 수동 검토할 수 있어야 한다. 자동 정상 판정이나 성공 처리로 바꾸지 않는다. `fallback=existing_path` 문자열만 반환하는 것으로 복귀를 검증했다고 하지 않는다.
- 원격 분석 서비스에서 모델을 한 번 로드하고 직렬 처리하는 안이다. 서버의 cold/warm 처리시간, 업로드/대기/응답 전송, 앱에서 실제 결과를 볼 때까지 걸린 시간을 분리한다. 서버가 3초 걸렸다고 사용자가 3초 기다린 것으로 기록하지 않는다.
- 기존 `BackTriageSuite`와 사진/구역 표시 개념을 재사용할 수 있다. `tools/back_triage_review.py`는 정적 E2 연습 도구이며 실제 모바일 앱/원격 API/저장 경로가 아니다. 고정 manifest를 통과하는 새 소비경로 계약이 필요하다.
- 현행 `LABELING_PROTOCOL.md`를 표시하고 기존 답을 재질문/자동 학습 편입하지 않는다. 기술적 접속/인증/설치 문제와 사람 라벨 정답은 구분한다.

- 실물 ID/확인 상태, 요청 ID/재전송 연결 ID, 모바일 앱/서버 API 버전, 지원 면, 입력 사진 ID/SHA·검토 상자/확인 여부(원본 경로는 최소화/로컬 관리).

- 앱 요청/업로드·서버 접수/시작/종료/앱 결과 표시, cold/warm 구분, 로딩/처리/사용자 대기시간, 성공·부분 보류·전부 보류·실패·미종결, 사유 코드.
- 결과 SHA와 연결된 사람 검토 완료/수정/추가 확인/판단 불가 및 검토시간. AI를 본 뒤의 판단은 독립 평가 정답이라고 부르지 않음.
- 충분히 확인한 정상 카드 집계는 결측을 정상으로 채우지 않고 선정·제외·판단 기준을 결과 전에 고정. 기존 완료 라벨을 새로 받았다고 표시하거나 다시 묻지 않음.
- Gemini/수동 검토의 비교는 같은 업무/분모에서 실제 사용 기록이 있을 때만 계산. 기준 호출 수·시간 기록이 없으면 절감률은 미측정이며 0이라고도 추정하지 않음. 0→0이 실제 확인되면 절감 0으로 기록.

기존 `pilot_record.append_line`을 사용할 수 있지만 `pilot_summary.py`는 listing-request-v1 전용이므로 back-triage 로그를 그대로 넣지 않는다. 새 범용 프레임워크를 만들기 전에 기존 보조도구의 고정 스키마로 최소 구현한다.

## 실행 순서와 아직 실행하지 않은 일

1. 확정된 안드로이드/현재 상시 PC에 맞춰 모바일 앱·원격 API 소비경로 작업 계약 고정. F2 기준안 방향/정식 기준 승인은 별개로 보존(입력/출력/실패/로그/소유 파일/함수 ≤7·새 경로 ≤4)을 고정.
2. 선택한 화면 최소 구현 및 합성 계약 검사. 기존 CLI 6전이 경로는 미해결 이력이며 새 소비경로에 그대로 이어 구조 기준을 통과한 것으로 처리하지 않음.
3. 설치 묶음 고정·깨끗한 환경·같은 소비 화면의 정상/장애/복구 검증 → F1 충족 여부 근거 대조.
4. 정식 F2 기준/시범 시작은 구체 조건과 승인 경로가 정해진 뒤 결정. 릴리스/설정/집계 기준 동결 후 기록 시작, 7일 시범이 지금 시작된 것으로 기록하지 않음.
5. 시범 결과를 기준대로 판단. 실패/부족도 그대로 보고하고 F1/F2 점수를 자동 추가하지 않음.

이번 미실행: 실제 화면 구현/서버 시작/배포/새 패키지 빌드·설치/모델 로드·실사진 추론/새 라벨/시범 수집·정상 카드 평가/전체 테스트/실제 업그레이드 복구. 모델 성능 FN·FP·분모·%p 변화와 일반화 개선은 이번에 미평가다.

## 안드로이드 + 상시 PC: F1 구현 순서 초안

### 첫 번째 검증 목표

휴대폰에서 사진 한 장을 선택하고 카드 상자를 확인한 뒤, PC의 고정 분석 릴리스가 반환한 구역을 **같은 사진의 정확한 위치**에 표시하고 검토 내용을 저장한다. 합성 입력/가짜 분석 응답으로 먼저 확인하고, 실제 모델·실사진 실행은 별도 검증 계획으로 구분한다. 미지원·실패 시 같은 사진의 수동 검토를 계속할 수 있어야 한다.

### 구현 순서

1. **PC 분석 접점:** 허용된 사용자가 올린 사진/실물 ID/요청 ID/검토 상자만 받는 입력 계약, 고정 릴리스 식별, 결과/보류 및 검토 저장 계약을 고정한다. 휴대폰이 임의 PC 파일 경로를 지정하는 API를 만들지 않는다. 원본 방향(EXIF)·좌표·사진 SHA 연결을 테스트한다.
2. **안드로이드 최소 화면:** 사진 선택 → 카드 상자 확인 → 전송/처리 상태 → 원본 사진과 종류별 점검 구역 → 사람 검토 저장. 현재 라벨 안내를 사용하고 요청/사진/결과 버전이 뒤섞이지 않게 한다. 로그인/접속 설정은 선택된 개인 원격 접속 방식에 맞춘 최소 범위다.
3. **실제 원격 왕복:** 승인된 연결에서 휴대폰 전송→PC→앱 결과 표시와 저장까지 확인한다. 같은 Wi-Fi 검사와 집 밖 검사 증거를 구분한다. 업로드/서버 대기·추론/응답·앱 표시까지 걸린 시간을 별도 기록한다. 앱을 닫거나 통신이 끊겨도 재전송이 별도 카드/성공 요청으로 중복 집계되지 않아야 한다.
4. **F1 설치/실패/복구:** APK 버전·서버 API/package/manifest/모델 SHA 조합을 고정한다. 깨끗한 설치, PC 미응답·중단, 잘못된 사진/상자, 지원 외 입력, 기록 실패에서 명시적 보류/수동 검토를 확인하고 이전 호환 조합으로 실제 복구한다. 이후 F1 충족 여부를 근거로 판단한다.
5. **F2 시작 조건:** 후면 점검 도구와 현행 F2의 앞뒤 쌍/손상 판정 불일치를 구체 기준안으로 정리해 사용자 검토를 받는다. 이 단계 전후에도 기존 점수/기준을 임의로 바꾸지 않는다. 실제 시범 시작/정상 카드 코호트/측정 경계는 사전 고정한다.

위 항목은 구현 계약 초안이다. 이번 준비 요청에서 앱 코드/원격 서버를 구현하거나 실행한 것은 아니다. 소스 수정 단계에는 정확한 소유 파일·함수 수(≤7)·새 호출 경로(≤4)와 테스트를 고정한다. 기존 CLI 6전이 위반 경로를 그대로 연결하고 기준 통과로 기록하지 않는다.

### 이번에 실제 확인한 개발 환경

- Android SDK 플랫폼 android-35/android-36, build-tools 35.0.0/36.0.0 디렉터리 확인. SDK 내 ADB 37.0.1 실행 확인.
- 기본 macOS java_home 탐지는 Java Runtime을 찾지 못했으나 Homebrew의 OpenJDK 17.0.21.0.2/27.0.1.0.3 바이너리는 직접 실행됐다. 새 Java 설치가 꼭 필요하다고 단정하지 않는다. 빌드에서는 실제 선택한 JDK 경로/Gradle/Android 플러그인 호환을 따로 고정·검증한다.
- 저장소에는 현재 AndroidManifest/Gradle 앱 프로젝트가 없다. Gradle 명령 경로 존재와 SDK/JDK 실행 확인만으로 APK 빌드 가능/휴대폰 연결 완료라고 주장하지 않는다.
- 실제 휴대폰 연결·APK 빌드/서명·설치·원격 PC 연결·서버 포트 개방은 하지 않았다. 접속 주소/인증값/페어링 정보도 수집하지 않았다.

이번 추가 변경은 문서 3개와 HTML 재생성뿐이다. 제품 코드/모델/라벨/진척 기준은 그대로다. 문서 검사는 확정된 플랫폼·호스트·F1 수용 단계의 일치와 HTML 파싱/diff 대조이며, 기존 12개 합성 테스트를 이번에 다시 실행한 것으로 세지 않는다.
