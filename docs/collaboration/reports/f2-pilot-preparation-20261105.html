## 먼저 결정할 두 가지

1. **실제 사용할 곳:** 추천은 현재 PC의 브라우저에서 여는 독립 후면 검토 보조도구다. 대안은 사용자가 이미 쓰는 별도 도구에 연결하는 것(도구 이름/연결 위치를 받아 조사). PokeCollector 연결과 기존 독립 CLI를 소비경로로 인정하는 것은 제안하지 않는다. 둘 다 기존 결정과 다르다.
2. **정식 F2로 무엇을 검증할지:** 현재 F2는 앞뒤 한 쌍 처리·거짓 손상 경고율을 요구하지만, 현재 모델은 후면의 점검/재촬영 우선순위만 제공한다. 추천은 후면 보조 사용에 맞는 **구체 기준안을 먼저 작성해서 사용자 검토를 받는 것**이다. 기준을 지금 바꾸거나 F2를 충족 처리하지 않는다. 현행 기준을 유지하면 지원 범위와 판정 의미의 불일치가 해결되기 전 정식 F2 완료 판정은 보류한다.

시범은 ‘앱을 만들어 놓고 요청 수를 채우는 일’이 아니다. 실제 사람이 사진을 확인하는 데 도움이 되는지, 오류가 나도 검토를 이어갈 수 있는지, 같은 릴리스의 기록으로 확인해야 한다.

## 추천하는 실제 사용 흐름 (제안, 미구현)

`내 PC 브라우저 → 후면 사진 선택 → 카드 실물 ID 지정/기존 ID 선택 → 카드 상자 확인 → 고정 릴리스의 지원 4칸 점검 → 사진 위 구역과 우선순위 확인 → 사람 판단·보류/수정·시간 기록`

- 실물 ID와 요청 ID는 다르다. 한 카드를 두 번 확인하면 요청은 2건, 실물은 1개다. 동일 실물 여부는 사용자 확인으로 묶고 사진 수/ID 개수를 자동으로 실물 수로 간주하지 않는다.
- 화면은 후면 엣지·모서리·표면의 점검 순위와 관찰 제한의 재촬영 참고 점수를 보여준다. ‘손상 확정/정상 확정/전체 완료’로 바꾸지 않는다. 앞면·센터링은 미지원/사람 검토로 표시한다.
- 오류/전부 보류이면 같은 사진에서 **수동 검토를 계속**한다. 소비경로가 없는 `fallback=existing_path` 문자열만 표시하는 것으로 복귀 완료를 주장하지 않는다. Gemini/다른 서비스 호출을 자동 추가하지 않는다.
- 같은 로컬 프로세스에서 모델을 한 번 로드하고 다음 요청을 직렬 처리하는 안이다. 최초 로딩(cold), 로딩 후 처리(warm), 사용자가 실제 기다린 전체 시간을 분리해 기록한다. 포트/실행 방식 등은 구현 계약에서 고정한다. 이번에 서버를 시작하지 않았다.
- 기존 `tools/back_triage_review.py`의 사진/구역 표현과 `BackTriageSuite`를 재사용할 수 있다. 다만 기존 도구는 사진 추론 후 정적 HTML을 만들어 답을 채팅으로 복사하는 E2 연습 경로다. 고정 release manifest를 사용하는 승인된 실사용 입력·저장 흐름으로 그대로 간주할 수 없다.
- 현행 `LABELING_PROTOCOL.md` 안내를 사용한다. 기존 라벨을 재질문하거나 시범 자료를 자동 학습으로 편입하지 않는다.

별도 도구 연결을 선택하면 위 흐름 중 사진/실물 ID 입력·결과 표시·수동 복귀·검토 기록이 그 도구의 어디에서 실행되는지 먼저 고정한다. 서비스 변경/배포 승인은 별도로 필요하다.

## 시범에서 모을 최소 기록 (설계안, 미구현)

- 실물 ID/확인 상태, 요청 ID, 지원 면, 입력 사진 ID/SHA·검토 상자/확인 여부(원본 경로는 최소화/로컬 관리).
- 정확한 릴리스·manifest·head/백본/wheel·소비 화면 버전, 장치·입력 크기·동시성 설정.
- 접수/시작/종료, cold/warm 구분, 로딩/처리/사용자 대기시간, 성공·부분 보류·전부 보류·실패·미종결, 사유 코드.
- 결과 SHA와 연결된 사람 검토 완료/수정/추가 확인/판단 불가 및 검토시간. AI를 본 뒤의 판단은 독립 평가 정답이라고 부르지 않음.
- 충분히 확인한 정상 카드 집계는 결측을 정상으로 채우지 않고 선정·제외·판단 기준을 결과 전에 고정. 기존 완료 라벨을 새로 받았다고 표시하거나 다시 묻지 않음.
- Gemini/수동 검토의 비교는 같은 업무/분모에서 실제 사용 기록이 있을 때만 계산. 기준 호출 수·시간 기록이 없으면 절감률은 미측정이며 0이라고도 추정하지 않음. 0→0이 실제 확인되면 절감 0으로 기록.

기존 `pilot_record.append_line`을 사용할 수 있지만 `pilot_summary.py`는 listing-request-v1 전용이므로 back-triage 로그를 그대로 넣지 않는다. 새 범용 프레임워크를 만들기 전에 기존 보조도구의 고정 스키마로 최소 구현한다.

## 실행 순서와 아직 실행하지 않은 일

1. 사용자 경로/기준안 준비 방향 선택 → 소비 화면 작업 계약(입력/출력/실패/로그/소유 파일/함수 ≤7·새 경로 ≤4)을 고정.
2. 선택한 화면 최소 구현 및 합성 계약 검사. 기존 CLI 6전이 경로는 미해결 이력이며 새 소비경로에 그대로 이어 구조 기준을 통과한 것으로 처리하지 않음.
3. 설치 묶음 고정·깨끗한 환경·같은 소비 화면의 정상/장애/복구 검증 → F1 충족 여부 근거 대조.
4. 정식 F2 기준/시범 시작은 구체 조건과 승인 경로가 정해진 뒤 결정. 릴리스/설정/집계 기준 동결 후 기록 시작, 7일 시범이 지금 시작된 것으로 기록하지 않음.
5. 시범 결과를 기준대로 판단. 실패/부족도 그대로 보고하고 F1/F2 점수를 자동 추가하지 않음.

이번 미실행: 실제 화면 구현/서버 시작/배포/새 패키지 빌드·설치/모델 로드·실사진 추론/새 라벨/시범 수집·정상 카드 평가/전체 테스트/실제 업그레이드 복구. 모델 성능 FN·FP·분모·%p 변화와 일반화 개선은 이번에 미평가다.

## 변경·검증·리스크·롤백

변경 파일은 본 준비안, `docs/collaboration/tasks/f2-pilot-preparation-20261105.md`, `docs/collaboration/reports/f2-pilot-preparation-20261105.html`뿐이다. 제품/모델/라벨/실험/진척 기준은 바꾸지 않는다. 실제 검사는 위 무결성 검사·합성 12테스트·문서의 기준/코드 대조·diff 검사이며, 원격 동기화 결과는 최종 인계와 로컬 sync.json에 기록한다.

롤백: 이번 문서 커밋만 `./develop -- git revert <SHA>` 후 일반 push. 코드/실험/라벨/진척 JSON은 변경하지 않아 데이터 복구나 운영 재시작이 필요 없다.
