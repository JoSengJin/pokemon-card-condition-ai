## 0. 결론

사용자가 모든 사진을 처음부터 끝까지 라벨링하는 구조에서 벗어날 방법은 **"카드 실물을 가진 협력 검수자가 지침대로 앞뒤를 직접 촬영하고 1차 라벨링을 하며, 사용자는 기준 예제와 불일치·판단 유보만 판정하는 구조"**다. 근거는 세 가지다.

3. 정상 중심 학습(PatchCore)과 합성 결함(CutPaste·DRAEM)도 **검증된 정상 사진과 실제 결함 평가 자료를 먼저 요구한다.** 그래서 병목을 우회하지 못한다. 2026-10-10 컨설팅 기록도 같은 판단이었다(`CONSULTING_CONSENSUS_20261010.md`).

## 4. 역할 분담 설계

| 담당 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **사용자** (기준 소유자) | 기준 예제를 승인한다. 이미 완료한 라벨을 재사용하고 다시 묻지 않는다. 두 사람의 불일치와 "판단 유보"를 최종 판정한다. 일치 항목 일부를 무작위로 감사한다. 지침 개정을 승인한다. | 명확한 사례를 전량 1차 라벨링하지 않는다(파일럿 기준 측정은 예외). |
| **협력 검수자** | 자기 카드를 지침대로 촬영하고, 출처·권리를 기록한다. 기준 예제 검사를 통과한 뒤 명확한 사례를 1차 라벨링하고, 애매하면 "판단 유보"로 둔다. | 모델 출력이나 AI 후보를 보고 라벨링하지 않는다. 다른 사람의 답을 보지 않는다. 판매글과 PSA 등급을 정답으로 쓰지 않는다. |
| **자동화** (기존 도구만) | 원본 SHA와 디코드 픽셀 SHA로 중복을 거른다. 기존 manifest와의 교차를 거부한다(A1 도구). coverage를 재계산한다(`data_coverage`). 검토 패킷을 만든다(A3 패턴). 두 사람의 응답을 단순 대조한 표를 만든다. 측정 시간 필드를 기록한다. | 정답을 만들지 않는다. AI 합의를 사람 정답으로 다루지 않는다. 미응답을 정상으로 채우지 않는다. |

### 협력자 유형 비교 (아직 확보한 사람은 없음)

| 유형 | 필요한 입력 | 장점 | 제약·위험 |
|---|---|---|---|
| 수집가 (지인, 커뮤니티) | 실물 카드 10~30장, 휴대폰, 지침 30분 숙지, 이 Mac의 검토 UI를 쓸 시간 | 플레이 흔적이 있는 카드가 많아 모서리·엣지 양성을 확보하기 쉽다. 자기 카드라 촬영 권리가 명확하다. | 사람마다 기준이 다르다. 일정을 보장할 수 없다. 좋은 카드 위주로 고를 수 있다. |
| 카드숍 | 매장 재고 촬영 허가, 직원 시간, 반출 금지 조건 확인 | 정상(미사용) 카드와 다양한 판본을 확보하기 쉽다. | 영업 사진 재사용 허락이 필요하다. 상품 가치 때문에 결함을 축소해 평가할 수 있다. 앞뒤 짝 관리가 필요하다. |
| 소규모 유급 작업자 | 표준 촬영 세트(실물은 사용자가 제공), 계약, 기준 예제 시험 | 시간을 예측할 수 있고 지침 준수를 강제할 수 있다. | 비용이 든다. 실물을 넘겨야 한다. 원격 UI가 없어 같은 장소에서 작업해야 한다(기존 검토 UI는 loopback 전용). |

연락 문안 초안은 [지침 초안](card-photo-labeling-guide-draft-20261025.md) 부록에 있다. **누구에게도 보내지 않았다.**

## 5. 최소 품질 절차

자세한 정의와 예시는 지침 초안에 있다. 핵심 절차는 다음과 같다.

1. **판정값 4종**: 정상(0), 결함(1), 관찰 불가(시야 제한 사유: glare/blur/obstruction/cropped/low_resolution/perspective/shadow), 판단 유보(미응답 = unknown). 관찰 불가와 판단 유보는 정상이 아니다.
2. **대표 예제**: 사용자가 이미 확인한 d manifest의 개발 사진에서 고른다(재질문하지 않는다). 질문마다 양성·정상·관찰 불가 예시를 둔다. 독립 시험(D1) 사진은 쓰지 않는다.
3. **독립 판정**: 각 검수자는 별도의 inventory 사본을 쓴다. 해당 inventory 옆에 `.drafts.json`(AI 초안)이 **없어야 한다**. 기존 UI는 이 파일이 있으면 AI 초안을 보여 준다(`card_condition/review.py`의 `draft_status`). 모델 점수, AI 후보 점, 다른 사람의 응답은 보여 주지 않는다.
4. **기준 예제 검사**: 1차 라벨링 전에 협력자가 기준 예제를 판정한다. 통과 기준은 파일럿에서 실측한 뒤 확정한다(제안값은 파일럿 계획에 있다).
5. **불일치 해결**: 두 원본 응답을 모두 보존한다. 사용자가 최종값을 정하고 근거 메모를 남긴다. 다수결이나 AI 판정으로 결정하지 않는다.
6. **무작위 감사**: 일치한 항목 중 사전에 정한 비율을 사용자가 다시 본다. 감사에서 오류가 나오면 해당 검수자의 묶음 전체를 재검토 대상으로 둔다.
7. **기록**: 검수자 ID, 지침 버전, 판정 시각, 소요 시간, 사진 원천과 권리, 원본 SHA와 디코드 SHA, 실물 그룹, 앞뒤 확인자를 남긴다.
8. **금지 구조**: 평가 정답을 만드는 사람이 평가 대상 모델의 답을 승인만 하는 흐름, 그리고 여러 AI의 동의를 사람 정답으로 취급하는 흐름. 메모리에 기록된 "hi 후보 미리 표시"는 개발용 라벨 보조 방식이다. **평가 정답 생성과 이번 파일럿에는 적용하지 않는다.**

## 6. 다음 검증 1개

[파일럿 계획](data-acquisition-pilot-plan-20261025.md)을 참고한다. 신규 10실물의 앞뒤 20면을 사용자(A)와 협력자(B)가 기존 검토 UI에서 서로의 답을 보지 않고 각각 판정한다. 이후 사용자가 불일치만 해결한다. 측정 항목은 카드당 작업시간, 질문별 불일치, 관찰 불가 비율, 사용자 최종 검토시간, 유효한 새 실물·판정단위 수다.

- 이 검증을 고른 이유: 이 검증은 "협력자 1차 라벨링이 사용자 노동을 줄인다"는 가설을 직접 측정한다. 외부 공개 자료 학습이나 PatchCore 기준선은 모델 실험이다. 둘 다 평가 자료 부족을 먼저 해결해야 결과를 해석할 수 있고, 이번 실행 경계(학습 금지) 밖이다.
- 결과를 A3·D1 충족이나 모델 성능 개선으로 보고하지 않는다. 파일럿 실물은 사용 이력이 남으므로 이후 D1 후보가 될 수 없다.

## 8. 변경 파일·검증·리스크·롤백

- 새 추적 파일 7개(`docs/collaboration/` 아래): task 1개, 보고서, 원천 비교표, 지침 초안, 파일럿 계획, 측정표 CSV, HTML. 기존 파일은 수정하지 않았다.
- 실행한 확인: d manifest·coverage SHA 확인(manifest가 ADOPTION과 일치), round2-live 저장 여부를 바이트 비교로 확인, 공개 페이지 읽기 전용 조사, 문서 수치와 coverage.json의 일치를 스크립트로 대조, HTML 정적 검사(스크립트·외부 링크·홈 경로 없음), 브라우저에서 열기. 결과는 task 문서 handoff에 기록한다.
- 미실행: coverage 재계산, 외부 자료 다운로드, 학습·추론·Gemini·Codex 호출, 사람에게 라벨 요청, 협력자 연락.
- 리스크: 공개 썸네일 표본은 첫 화면 50개뿐이라 자료 전체 품질을 대표하지 않는다. Roboflow 수치는 페이지 표시값이다. 협력자 판정 기준이 사용자와 다를 수 있으며, 파일럿은 이것을 측정하려는 것이다. 파일럿 제안 수치는 사전 근거가 없는 제안값이다.
- 롤백: 문서만 추가했으므로 통합 전이면 반영하지 않고, 통합 후라면 `git revert`. 데이터, 모델, manifest 복구는 필요 없다.
