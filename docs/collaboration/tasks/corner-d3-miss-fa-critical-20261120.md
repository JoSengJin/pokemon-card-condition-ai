## 확인된 사실
1. D3(5점, pending) 완료 조건: 실물 단위 "하나라도 누락" 사건률과 "하나라도 오탐" 사건률의 단측 95% Wilson 상한이 각각 ≤10%, ≤20%. D2 모서리 분모는 양성 72·정상 56이라 누락 ≤3/72(상한 0.0998), 오탐 ≤6/56(상한 0.194)이어야 한다. 현재 D2 저장 점수: 누락 9/72(상한 0.203), 오탐 20/56(0.467) (d3-event-rates-20261113.md, 사건 정의 L).
2. 사건 정의 L: 결함 실물에서 결함 구역 하나라도 점수 <0.281(낮음 임계)이면 누락, 정상 실물에서 구역 하나라도 ≥0.509(높음 임계)이면 오탐. 두 임계는 개발 OOF 결함 구역 점수의 10·30분위로 **결과 전에 동결**됐다(PROGRESS_CRITERIA C2).
3. 개발 OOF(기록 artifacts/experiments/20261102T140143-82781117, 후보 E, 946구역·257그룹)를 L로 계산: 누락 37/176(상한 0.265), 오탐 17/81(0.293), 풀링 AUC 0.8565, 같은 사진 AUC 0.796. D2와 분모가 달라 서로 개선으로 비교하지 않는다.
4. 입력 224 시험(기록 artifacts/experiments/20261120T144747-d3c69a9b, completed): 누락 69/176, 오탐 30/81, AUC 0.745로 크게 악화. 해상도가 병목이라는 신호이나 개선 후보는 아니다. 672 계획서가 있으나 승인·구현 전이다(기대 효과는 포화 가능성이 커 불확실).
5. 이 세션이 계산한 구조적 사실(개발 OOF, 후보 E 점수; 직접 재계산해 확인할 것):
   - 낮음 임계 0.281은 결함 구역 점수의 10분위라, 구역 단위로 결함 구역의 10.1%가 구조적으로 낮음 구간에 들어간다. 양성 사진당 결함 구역이 평균 2.3개라 "하나라도" 규칙이 사진 단위 누락을 21%로 키운다.
   - 낮음 임계만 내리면 누락은 곧바로 줄어든다(L 누락: 0.281→37/176, 0.20→21, 0.15→13, 0.10→6, 0.08→4). 대신 정상 구역 중 "낮음"으로 분류되는 비율이 0.281에서 58%, 0.15에서 34%, 0.10에서 18%로, 낮음 구간이 결함을 거르는 정보가 줄어든다. 누락 ≤11/176(상한 ≤0.10)은 임계 약 0.12 부근이다(미확인: 정확한 값은 직접 구할 것).
   - 높음 임계도 같다: 0.509→오탐 17/81, 0.6→10, 0.7→7, 0.8→4. 대신 결함 구역 중 높음 구간 비율이 70%→61%→49%→36%로 줄어든다.
   - 즉 D3의 누락·오탐 수치는 **임계(작동점)를 얼마나 옮기는가**에 크게 좌우되고, 모델 개선은 같은 임계에서 결함·정상 점수가 얼마나 벌어지는가(분리도)로만 기여한다.

## 비판적으로 따질 질문 (설계 전에 답을 근거로 적는다)
Q1. D3를 통과시키는 일과 "카드 상태 누락·오탐을 실제로 줄이는 일"은 같은가? 임계만 옮겨 통과하면 낮음/높음 구간이 정보를 잃는데 그것을 개선이라 부를 수 있는가? 동결 임계 변경은 결과를 본 뒤의 기준 변경이므로 사용자 승인 없이 하지 않는다. 승인을 요청한다면 임계를 옮겼을 때 낮음·높음 구간의 정보 손실(위 5번 수치)을 함께 제시한다.
Q2. 해상도(448→672)가 분리도를 의미 있게 올릴 근거가 있는가? 원본 모서리 크롭이 250~350px이라 448이 이미 확대 입력이다. 224가 나빴다는 것은 방향 신호일 뿐이다. 기대 이득이 작은 실험에 시간을 쓰기 전에 대안과 비교한다.
Q3. 놓친 결함 구역 41곳(개발 OOF)의 원인은 모델인가 라벨인가? 사용자는 확대해 화이트닝을 결함 처리한다(엄격한 라벨, memory appraiser-zoom-whitening-labels). 낮은 점수를 받은 "결함" 구역을 눈으로 보고 라벨 경계 잡음인지 확인한다. 확인은 읽기 전용이고, 사람 정답을 모델 오답을 이유로 바꾸지 않는다. 라벨 재판정이 필요하면 사용자에게 요청한다(재요청 금지 규칙: 이미 완료한 라벨을 다시 묻지 않는다, 새 근거가 있을 때만).
Q4. 오탐 20/56(D2)의 원인은 무엇인가? 정상 사진이 "하나라도" 구역 오탐으로 잡히는 구조다. 정상 구역 중 높음으로 분류되는 구역(개발 OOF 15%)의 공통점(위치·해상도·반사·인쇄 무늬)을 읽기 전용으로 분류한다.
Q5. 사진 단위로 집계하는 방식(예: 구역 점수를 하나로 합치는 규칙)이 D3 정의와 맞는가? 정의 변경은 승인 사안이다.

## 개발 규칙 (위반하면 중단)
- 소스(worker·모델) 생성·수정은 `./develop -- <명령>` 안에서만. 먼저 `./develop --check`. 새 실험은 `./experiment --plan <plan.json> -- <실행 명령>`으로만, 가설 ID 고유·변경 변수 1개·대조 경로·사전 수치 성공/실패 기준 필수. 결과를 본 뒤 기준을 바꾸지 않는다. 이 세션은 worker를 `./develop` 밖에서 한 번 잘못 만들었다가 바로잡았다: 같은 실수를 반복하지 않는다.
- 학습·평가 사진 그룹 분리. D1 봉인 시험셋·D2 시험 자료를 학습·튜닝에 쓰지 않는다(D2 모서리는 후보 E가 소진했다. 새 후보로 D3 독립 통과를 주장하려면 새 독립 라벨 자료와 사용자 결정이 필요하다).
- Gemini 호출 0, 운영 코드(PokeCollector)·운영 Gemini fallback 변경 금지, 동결 임계·진척 기준·배점 변경은 사용자 승인 사안.
- 테스트를 먼저 쓰고 실패를 확인한다. 공유 코드를 복사해 확장하면 기존 조건에서 출력이 같은지 동등성 테스트를 먼저 둔다.
- 검증된 변경은 기능별 커밋하고 `./develop -- git push origin main`(SHA별 사용자 직접 승인 뒤, 사람이 직접 연 메인 세션만). force push·이력 재작성 금지. 커밋 끝에 현재 세션 지침의 Co-Authored-By 줄.
- 모델 성능을 평가한 턴에는 사진 위 구역별 사람 정답·모델 출력·누락/오탐 분모 HTML을 갱신해 연다(독립 아님·개발 OOF 구분). 합성 테스트만이면 합성이라 적는다.
