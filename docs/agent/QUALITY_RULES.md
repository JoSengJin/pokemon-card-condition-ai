# 실험·라벨·판정 품질 규칙 (2026-11-25)

**상태: 문서 적용본.** main에 통합된 뒤의 새 작업부터 적용한다(통합 전 브랜치에서는 효력이 없고, 과거 실험·라벨·판정에는 소급하지 않는다). 규칙별 실제 적용 상태는 7절 표가 정본이다. 규칙 본문은 이 문서 한 곳에만 두고 다른 문서는 이곳을 가리킨다. 이 문서는 새 개발·학습·외부 호출·라벨 재요청을 승인하지 않으며 기존 사전 기준·잠금·역할 규칙을 바꾸지 않는다. 기존 규칙과 부딪히면 기존 규칙이 우선한다.

**범위는 특정 모델이나 특정 오류가 아니라 모든 칸의 실험·라벨·판정이다.** 칸 = 표면·엣지·모서리·관찰 제한·센터링 등 판정 대상의 종류. 규칙마다 "언제 / 무엇을 / 어디에 적는가"만 정한다. 수치 문턱은 본문에 박지 않고 "사용자가 정한 값"으로 둔다. 정해지기 전에는 그 규칙의 문턱 부분만 미적용이다. 특정 실험·카드·오류 장수를 규칙 조건으로 넣지 않는다.

규칙 16개 = 먼저 쓴 4개(`error-cause-triage`·`chance-check`·`worker-review-checklist`·`experiment-closeout`) + 후보 목록([SHORTLIST.md](../collaboration/plans/ecc-adapted-practices-20261125/SHORTLIST.md))의 14개. 후보 R4는 `error-cause-triage`에, R9는 `experiment-closeout`에 합쳐서 항목 수는 16이다. 각 규칙 제목 끝의 괄호는 후보 번호다. 규칙은 이름으로 부르고, 2026-11-25 이전 기록의 번호(Q01~Q16)는 7절 표의 "옛 번호"로 찾는다. **이름을 외울 필요는 없다.** 에이전트가 [품질 규칙 선택표](../AGENT_START.md#품질-규칙-선택표)에서 상황에 맞는 규칙을 고른다.

**용어**: 누락 = 결함을 놓침. 오탐 = 정상을 결함으로 잘못 표시. 평가 자료 = 실험 실행기가 `reference.json`에 고정한 행 묶음(`cohort_sha256`으로 구분). worker = 실제 학습·평가를 수행하는 실험 스크립트. AI 판정 = 언어 모델이 사진 조각을 보고 내린 판정(사람 라벨과 분리해 보관). 판정 단위 = 그 칸의 기존 단위(카드·사진·구역).

## 1. 판정 기준 관리 — 사람 라벨과 AI 판정 공통

### `single-source-criteria` · 기준의 정본은 하나다 (R1)
- **언제**: 어떤 칸의 결함·정상·판단 불가 정의를 새로 쓰거나 고칠 때. 사람 라벨 화면이나 AI 판정 지시서를 만들거나 고칠 때.
- **무엇을**: 칸마다 정의를 정본 한 곳에만 쓴다. 사람 화면과 AI 지시서는 정본을 그대로 가져오거나, 다르게 쓴 줄을 "사람 기준과 다른 점" 표(무엇이, 왜 다른가)로 밝힌다. 바꿀 때는 정본 → 다른 점 표 → 화면·지시서 순서로 바꾼다.
- **어디에**: 정본 위치는 `LABELING_PROTOCOL.md`가 가리킨다. 다른 점 표는 해당 지시서 머리에 둔다.
- **지킬 것**: 기준이 다르다고 밝힌 판정끼리는 같은 분모로 누락·오탐·일치율을 비교하지 않는다. 표에 없는 차이가 발견되면 결함으로 기록한다(`regression-for-every-fix`).

### `label-provenance` · 라벨마다 "그때의 기준과 화면"을 남긴다 (A3)
- **언제**: 사람 라벨이나 AI 판정을 새로 저장할 때.
- **무엇을**: 판정마다 기준 문구 버전과 그때 보여 준 사진 조각의 해시를 함께 저장한다. 과거 판정은 소급해서 채우지 않고 "버전 미상"으로 둔다.
- **어디에**: 라벨·판정 저장 형식. 일치율·누락·오탐을 보고할 때 기준 버전별로 분모를 나눠 적는다.
- **지킬 것**: 버전이 다르다는 이유로 정답을 자동으로 바꾸지 않는다. 표시만 한다.

### `judge-before-peeking` · 마지막 판정자는 자기 판정을 먼저 적는다 (R5)
- **언제**: 앞선 판정들이 엇갈린 대상을 한 판정자(사람 또는 AI)가 최종 결정할 때.
- **무엇을**: 앞선 판정을 열기 전에 원본만 보고 자기 판정·확신·근거 한 줄을 기록한다. 그 뒤 앞선 판정을 보고 바꾸면 이유를 남긴다.
- **어디에**: 판정 결과 기록. "먼저 적은 판정에서 바뀐 수 / 엇갈린 수"를 함께 보고한다.
- **지킬 것**: 먼저 적은 기록이 없으면 그 최종 판정은 "독립 확인 아님"으로 표시한다.

### `explicit-verdict-merge` · 여러 번 판정한 결과는 병합 기준을 밝힌다 (A2)
- **언제**: 같은 대상을 두 번 이상 판정해 하나로 합칠 때.
- **무엇을**: 두 기준을 구분해 적는다. **민감 병합** = 한 번이라도 결함이면 결함(놓침을 줄이지만 판정 횟수가 늘수록 결함 비율이 커진다). **안정 병합** = 모든 판정이 같을 때만 그 판정. 엇갈린 대상은 "불확실"로 따로 둔다.
- **어디에**: 판정 보고에 대상별 일치율, 민감 병합 결함 비율, 단일 판정 결함 비율을 나란히 적는다.
- **지킬 것**: 같은 모델·같은 지시서·같은 사진 조각으로 반복한 판정은 독립된 확인 여러 개로 세지 않는다. "불확실"은 학습 라벨에도 사람 라벨에도 섞지 않는다.

### `label-agreement-watch` · 재판정 일치율에 목표선과 경고선을 둔다 (R7)
- **언제**: 칸별로 같은 판정자의 재판정 일치율을 잴 때. 기준 문구가 바뀌었을 때(그 칸은 "다시 잴 대상"으로 표시).
- **무엇을**: 결과를 보기 전에 칸마다 목표선과 경고선을 정해 문서에 고정한다. 분모가 사용자가 정한 최소 분모보다 작으면 "미측정"이다. 경고선 아래인 칸은 그 칸 라벨로 모델 가설을 내기 전에 기준 문구와 제시 방식부터 점검한다(`error-cause-triage`의 라벨 쪽).
- **어디에**: `LABELING_PROTOCOL.md`의 라벨 일치도 관리 절.
- **지킬 것**: 값은 `LABELING_PROTOCOL.md` "라벨 일치도 관리"에 고정한다. 재판정 대상을 새 라벨 묶음에 섞는 것은 완료 라벨 재요청이므로 비율과 장수를 정해 사용자 승인을 받은 뒤에만 한다.

### `label-screen-round-trip` · 라벨 화면은 "누른 것 = 가져온 것"을 시험한다 (R8)
- **언제**: 라벨 화면이나 답 가져오기 도구를 만들거나 바꿀 때.
- **무엇을**: 화면 스크립트를 실제로 실행해 누르는 순서를 재현하고, 나온 답을 실제 가져오기 도구로 읽은 결과가 누른 상태·대상 ID와 같은지 시험한다.
- **어디에**: 해당 화면 시험 옆. 실행 환경이 없어 건너뛰면 "미검증"으로 적는다.
- **지킬 것**: 어긋남을 찾으면 그 화면으로 받은 기존 답을 정답 변경 없이 영향 감사 대상으로 기록한다.

## 2. 평가 자료

### `fresh-labels-test-first` · 새 라벨 묶음은 학습에 넣기 전에 한 번만 평가한다 (A1)
- **언제**: 사람이 확인한 새 라벨 묶음이 들어왔을 때.
- **무엇을**: 학습·모델 선택·기준 조정에 쓰기 전에, 현재 채택 모델을 그대로 두고 그 묶음을 한 번 평가한다. 이 한 번이 독립 시험이다. 평가 뒤에는 개발 자료로 옮길 수 있고, 옮긴 뒤에는 독립이라고 다시 부르지 않는다.
- **어디에**: 평가는 공통 실험 실행기로 사전 계획과 함께 실행한다. 보고서에 독립 시험 분모를 개발 자료와 따로 적는다.
- **지킬 것**: 이 규칙은 평가 실행을 승인하지 않는다(실험 승인은 기존 절차). 모델 결과로 골라 모은 라벨 묶음은 치우쳐 있으므로 독립 시험으로 쓰지 않는다. 묶음이 작으면 신뢰구간과 함께 "판정력 낮음"이라고 적는다.

### `zero-denominator-unmeasured` · 분모가 0인 상한은 통과가 아니다 (R6)
- **언제**: 평가 자료에 결함 행이 없거나 정상 행이 없을 때.
- **무엇을**: 누락 상한은 결함 행이 1 이상일 때, 오탐 상한은 정상 행이 1 이상일 때만 통과로 센다. 분모가 0이면 그 상한은 "미측정"이다. 계획에는 평가 자료마다 결함·정상 행 수를 적는다.
- **어디에**: 실험 계획과 결과. 한쪽 정답만 담은 회귀 평가는 그 사실을 계획에 밝히고 나머지 상한으로만 판정한다.
- **지킬 것**: 실행기는 결과에 상한별 상태(`acceptance_caps`)를 `passed`/`failed`/`unmeasured`로 남기고, 계획의 `evaluation_counts`를 실제 행과 대조한다([공통 실험 기록](../../COMMON_EXPERIMENT_RECORDS.md)). `unmeasured`를 통과로 세지 않으며 보고에 "미측정"과 이유를 적는다. 과거 계획·기록의 판정은 바꾸지 않는다.

## 3. 실험 전

### `error-cause-triage` · 오류 원인 분류 — 다음 모델 가설을 내기 전에 (먼저 쓴 규칙 + R4)
- **언제**: 실험이 사전 기준에 못 미쳐 끝났고(`result.acceptance_passed=false`), 같은 평가 자료로 새 모델 가설을 내려고 할 때.
- **무엇을**: 남은 누락·오탐을 하나씩 아래 묶음 중 하나에 넣는다. 묶음마다 "근거 있음"(기록된 사람 재판정 등)과 "의심(미확인)"을 구분한다.

| 묶음 | 뜻 | 그 묶음이 허용하는 다음 행동 |
|---|---|---|
| 라벨 쪽 | 사람 정답이 틀렸거나 기준이 애매함 | 재판정 대상 목록 제안만. 완료 라벨 재요청은 사용자 승인 뒤 |
| 사진 조건 | 원본 사진 자체가 판단할 수 없게 찍힘(가림·반사·저해상도 등) | 판정 보류·관찰 제한 처리, 입력 기준 진단 |
| 입력 경로 쪽 | 원본은 괜찮은데 우리가 만든 상자·자르기·축소·방향·저장된 특징이 어긋남 | 전처리 수정 가설만. 사전 기준과 필수 평가는 그대로 |
| 모델 쪽 | 사진·입력·정답이 분명한데 모델이 틀림 | 모델 가설 (모델 변형을 정당화하는 유일한 묶음) |
| 기준 쪽 | 작동점·정의 때문에 갈림 | 기준 진단. 작동점 이동은 정확도 향상으로 부르지 않는다 |
| 판단 불가 | 위 어디에도 넣을 근거가 없음 | 그대로 둔다. 정상·결함으로 채우지 않는다 |

- **지킬 것**
  - 분류 규칙을 사진·점수를 보기 전에 적어 커밋한다. 가능하면 비교용 대상을 섞고 번호만 보고 관찰한다.
  - "모델 쪽"에 넣으려면 그 대상의 원본 해상도·잘라 낸 크기·상자를 먼저 적고 입력 경로 문제가 아님을 확인한다. 확인하지 못하면 "판단 불가"다.
  - 에이전트의 사진 관찰은 사람 라벨이 아니다. 이 분류로 정답을 바꾸지 않는다.
  - 결과는 장수로만 쓴다. 분류 대상은 모델 결과로 고른 표본이라 치우친다는 한계를 함께 적는다.
- **어디에**: 다음 계획의 `hypothesis` 문장에 분류 보고서 경로, 겨냥하는 묶음, 그 묶음의 장수를 적는다.

### `can-this-experiment-tell` · 판별 가능성 관문 — 이 실험이 결과를 가릴 수 있는가 (A4)
- **언제**: 새 모델·전처리 가설의 계획을 쓸 때. 새 라벨을 요청할 때.
- **무엇을**: 계획에 세 수를 나란히 적는다. ① 겨냥한 묶음의 장수(`error-cause-triage`), ② 사전 기준을 채우는 데 필요한 개선 장수, ③ 그 칸의 라벨 흔들림 장수(같은 판정자 재판정 불일치, 사람·AI 불일치 중 측정된 것). ①이 ②보다 작거나 ②가 ③보다 작으면 그 가설은 내지 않는다. 새 라벨을 요청할 때는 "몇 장을 보고 오류가 몇 개 이하면 채택"과, 좋은 모델을 버릴 위험·나쁜 모델을 받을 위험을 미리 적는다.
- **어디에**: 실험 계획의 `hypothesis`와 새 라벨 요청 문서.
- **지킬 것**: ③이 측정되지 않았으면 "미측정"으로 적고, 그 사실을 판별력의 한계로 보고한다. 미측정을 0으로 치지 않는다.

### `stop-repeated-misses` · 같은 평가 자료에서 연속으로 미달하면 모델 가설을 멈춘다 (R3)
- **언제**: 같은 평가 자료에서 모델 가설이 사전 기준에 연속으로 못 미친 횟수가 사용자가 정한 값에 닿았을 때.
- **무엇을**: 그 평가 자료로는 새 모델 가설을 내지 않는다. 다음 계획은 `error-cause-triage`의 라벨 쪽·사진 조건·입력 경로 쪽·기준 쪽을 겨냥한 진단이나 자료 요청 제안만 할 수 있다. 모델 경로를 다시 열려면 새 평가 자료나 사용자 결정이 필요하다.
- **어디에**: 실험 계획에 "이 평가 자료의 연속 미달 횟수"를 적는다(`chance-check`의 시도 수와 함께).
- **지킬 것**: 이것은 세션 중단 조건이 아니다. 다른 독립 작업은 계속한다. 횟수 값은 `COMMON_EXPERIMENT_RECORDS.md` "품질 규칙 연결"에 고정한다.

## 4. 실험 후

### `chance-check` · 우연과 반복 시도 표기 — 같은 평가 자료로 두 결과를 비교할 때 (먼저 쓴 규칙)
- **언제**: 대조 결과와 후보 결과를 같은 평가 자료에서 비교해 보고할 때마다.
- **무엇을** (판정 단위는 그 칸의 기존 단위)
  1. 누락·오탐 각각 `장수/분모`와 95% 신뢰구간(윌슨 구간: 장수가 적을 때 비율이 흔들리는 범위).
  2. 짝지은 변화: 새로 틀린 장수, 고쳐진 장수, 정확 검정 p값.
  3. 같은 평가 자료(`cohort_sha256`)에 쌓인 실행 수와 이번이 몇 번째 시도인지.
  4. 학습에 무작위성이 있으면 실행 간 편차. 계획에 미리 선언한 경우에만 여러 시드로 잰다. 선언이 없으면 "단일 실행, 실행 간 편차 미측정"이라고 적는다(동일 입력 반복 학습 금지는 그대로다).
- **도구**: 모서리 카드 단위는 아래 도구로 1~3을 얻는다. 다른 칸은 같은 항목을 그 칸의 단위로 계산하며, 이 도구가 그 칸을 지원한다고 쓰지 않는다.

```sh
.venv/bin/python tools/diagnostics/corner-chance-check-20261124/check.py 대조/result.json 후보/result.json artifacts/experiments
```

- **읽는 법**
  - 이 수치는 기술 통계다. 사전 기준(`acceptance`)을 대신하거나 완화하지 않는다.
  - 구간이 크게 겹치거나 새로 틀림·고쳐짐의 합이 작으면 "우연 범위 안"이라고 쓰고 향상이라고 부르지 않는다.
  - 시도 수는 하한이다. 시도가 쌓일수록 한 번의 통과는 덜 믿는다.
  - 독립 자료(`fresh-labels-test-first`)로 확인하기 전에는 "일반화 개선 미확인"이다.

### `experiment-closeout` · 실험 보고서의 세 칸 — 통과·미달과 무관하게 (먼저 쓴 규칙 + R9)
완료된 실험의 보고서 끝에 세 줄을 둔다. 비어 있으면 "없음"과 이유를 적는다.
- **얻은 교훈**: "다음에 [기록에서 확인할 수 있는 신호]가 보이면 [행동]한다" 형식으로 쓴다. 쓰기 전에 기존 교훈을 원인 낱말로 찾아, 같은 원인이면 새로 쓰지 않고 기존 항목에 실험 ID만 더한다. 다음 가설을 내기 전에 교훈 목록의 신호와 대조한다.
- **추가한 회귀 평가**: 이번에 확인한 오류를 필수 평가(`required_cohorts`)에 넣었는지, 넣지 않았다면 이유. 모델 밖의 결함은 `regression-for-every-fix`을 따른다.
- **남긴 부채**: 임시 기준·미검증·건너뛴 검사와 갚는 조건.

### `regression-for-every-fix` · 고친 결함은 실제 입력으로 회귀 검사를 남긴다 (R2)
- **언제**: 라벨 화면 문구·AI 판정 지시서·worker·도구에서 확인된 결함을 고칠 때.
- **무엇을**: 실제로 문제가 된 입력(잘못된 문구 원문, 놓친 대상의 ID와 원본)을 그대로 쓰는 회귀 검사를 함께 남긴다. 더 쉬운 비슷한 입력으로 바꾸지 않는다. 자동 검사가 불가능하면 수동 확인 절차·마지막 확인 날짜·미확인 사유를 적는다.
- **어디에**: 해당 코드의 시험 또는 지시서 옆 회귀 목록.
- **지킬 것**: 회귀 검사도 수동 확인 기록도 없으면 그 결함은 "미해결"로 보고한다. 회귀 목록의 사례는 결함 때문에 고른 것이라 성능 분모와 섞지 않는다.

## 5. 코드 리뷰

### `worker-review-checklist` · 실험 worker 리뷰 점검표 (먼저 쓴 규칙)
worker나 모델 코드의 리뷰 입력에 아래 8줄을 넣는다. 실행기가 이미 일부를 검사하는 항목도 리뷰어가 코드에서 다시 확인한다.
1. **분리**: 같은 카드(group)·같은 사진·같은 판매글이 학습과 평가에 함께 들어가지 않는가. worker가 스스로 검사하고 어기면 실패로 끝나는가.
2. **평가 자료로 고르기**: 임계값·설정·특징 선택·조기 종료가 평가 행을 보고 정해지지 않았는가.
3. **전처리 일치**: 학습·평가·소비 경로의 자르기·해상도·방향·정규화가 같은 코드에서 나오는가.
4. **정답 보호**: 라벨 파일을 쓰지 않는가. 미확인을 정상·결함으로 채우지 않는가. AI 판정이 사람 라벨과 섞이지 않는가.
5. **조용한 실패**: 빠진 행·읽지 못한 사진·유한하지 않은 점수를 기본값으로 메우지 않고 실패로 끝내는가.
6. **재현**: 시드, 입력 SHA, 저장된 특징의 출처(backbone·자르기 버전)를 기록하는가. 저장된 특징이 현재 전처리와 같은 버전인가.
7. **변수 하나**: diff가 계획의 `change`에 적힌 것 외의 동작을 바꾸지 않는가.
8. **기준선**: 대조 점수가 `reference.json`의 `before_scores`에서 오는가. 후보 점수를 복사해 넣지 않았는가.

확인하지 못한 줄은 "미확인"과 이유를 적는다. 통과로 채우지 않는다.

## 6. 요청 해석

### `short-request-reading` · 짧은 요청 해석 규칙 (A5)
에이전트가 짧은 요청을 받았을 때 스스로 지킨다. 사용자가 요청 문구를 바꿀 필요는 없다.
1. 짧은 요청은 같은 세션의 직전 맥락과 현재 TODO로 목표를 채운다. 질문은 답이 결과를 바꾸고 추론할 근거가 없을 때만, 한 번에 하나, 추천을 표시해 묻는다. 사소한 결정은 가정을 한 줄 적고 진행한다.
2. 시작할 때 한 줄로 적는다: 목표 / 하지 않을 것 / 완료 기준(같은 분모의 수치 또는 직접 확인한 화면) / 확인 방법.
3. 모델·라벨 작업에서는 카드 상태 감정 전문가의 관점(칸별 기준, 촬영 조건, 판단 불가 처리, 판정 일관성)과 카드 이미지 모델 수석 개발자의 관점(라벨 흔들림, 오류 원인 분류, 학습·평가 분리, 작은 분모의 우연)에서 요청에 빠진 점검을 스스로 붙이고, 보고에 "추가한 점검"으로 표시한다.
4. 개선을 주장하기 전에 원인 근거(사례·파일·수치)를 먼저 댄다. 같은 개발 자료에서 반복 실험해 통과한 것은 "우연 가능"으로 보고한다.
5. "열었다·고쳤다·저장됐다"는 실제로 열어 보거나 실행하거나 다시 읽어 확인한 경우에만 쓴다. 확인하지 못한 것은 미확인이라고 적는다.
6. 보고는 결론 한 줄 → 근거 → 쉬운 설명 순서로 쓴다. 내부 약칭은 처음 나올 때 풀어 쓴다. 다른 사람이나 다른 에이전트에게 넘길 글은 받는 쪽이 이 대화를 모른다고 가정하고 복사 블록 하나로 준다.
7. "권장대로"·"진행"은 직전에 제안한 범위 안에서만의 위임이다. 범위 밖 규칙 신설이나 다른 에이전트의 계약 변경은 하지 않고 제안으로만 남긴다.

요청 틀의 근거 자료(사용자 요청 분석)는 공개하지 않아 통합본에 없다. 기존 지침과 대조한 결과 부딪히는 줄은 찾지 못했다(개발 완료 보고의 "진척률·성과 한 줄 먼저"는 6번의 "결론 한 줄"에 해당한다).
