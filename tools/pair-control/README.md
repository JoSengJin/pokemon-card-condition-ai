# pair-control — Codex·Claude 병렬 개발 관제 (로컬, mock 기본)

사람이 작업 배정·시작·중단·검토·통합 승인을 제어하는 로컬 도구다. 관리용 LLM은 없다. 모든 단계는 결정적인 workflow 단계와 실행기 함수다.

| 구성 | 역할 |
|---|---|
| Mastra Workflow `prepare-task` | `plan → create-worktree → register(계약 커밋)` |
| Mastra Workflow `pair-task` (`src/workflow.ts`) | `launch → await-exit → collect(Git 계약 검사) → review-gate(작업 테스트·리뷰·사람 승인) → integrate-gate(통합·통합 후 검사)` 단계·분기(bail)·suspend/resume·실행 기록(LibSQL) |
| Node 실행기 (`src/executor/`) | 계약 검증, 충돌·중복 차단(O_EXCL 잠금), detached 감독 프로세스, 취소, 재시작 복구, Git 검사, `./develop` 안 cherry-pick |
| Mastra Studio (`/`) | workflow 그래프·실행 목록·trace (Mastra 기본 기능 그대로 사용) |
| 관제 화면 (`/pair`) | Studio에 없는 작업 배정·프로세스 제어·결과 검토·통합 승인만 담당. `src/ui/page.html`(마크업·스타일) + `src/ui/js/*.js` 모듈(`/pair/static/<이름>.js`로만 제공) |

## 실행

Node 22 이상이 필요하다(`.nvmrc`=24, `engine-strict`). 로그인 셸 기본 Node가 18이면 `nvm use 24` 후 실행한다. `npm start`도 Node 버전을 검사해 거부한다.

```sh
cd tools/pair-control
npm ci
npm test                      # mock 프로세스 검증(모델 요청 없음)
npm run demo:fixture          # .demo/에 합성 저장소·worktree 생성
npm start -- --demo           # http://127.0.0.1:4111/pair , Studio http://127.0.0.1:4111/
```

실제 저장소에 쓰려면 `config.example.json`을 `config.local.json`(Git 제외)으로 복사해 절대경로를 넣고 `npm start`. 상태·로그·Mastra DB는 `.state/`(Git 제외)에 저장된다. `npm install` 시 npm 11 기본 정책으로 esbuild/fsevents install script가 막히지만 optional 바이너리 패키지로 동작한다(이 환경에서 확인).

## 세 가지 실행 모드

| 모드 | 에이전트는 누가 | 도구가 하는 일 |
|---|---|---|
| **수동(기본)** | 사용자가 Claude/Codex 세션을 해당 worktree에서 직접 실행 | 소유권 잠금(파일 겹침 방지), 시작 프롬프트 생성, "작업 완료" 후 검사·인계·승인·통합·푸시. 프로세스를 띄우지 않으므로 구독 로그인만 쓰는 경로 |
| 실제 CLI | 도구가 `claude`/`codex` CLI를 실행(구독 로그인) | 위 + 프로세스 감독·중단. **무과금 가드를 모두 통과해야 시작** |
| 연습(mock) | 가짜 스크립트 | 도구 동작 확인용. 코드 품질 검증이 아님 |

## 새 작업 만들기 (자동 준비)

사람은 **담당(Claude/Codex) · 목표 · 고칠 파일**만 정한다. 완료 조건·작업 테스트·실행 환경·충돌 그룹 같은 나머지는 기본값이 있고 "고급 설정"에 접혀 있다. 나머지는 Mastra `prepare-task` workflow(`plan → create-worktree → register`, 관리용 LLM 없음)가 채운다.

| 값 | 자동 규칙 |
|---|---|
| task ID | `task-<MMDD>-<n>` (겹치지 않는 번호) |
| 브랜치 | `<담당>/<task ID>` — 이미 있으면 거절(덮어쓰지 않음) |
| 기준 SHA | 통합 브랜치(`integration.branch`) 최신 커밋 |
| worktree | `<worktreeRoot>/<저장소 폴더명>-<담당>-<task ID>`, `git worktree add -b`로 생성. `worktreeRoot`를 비우면 저장소의 상위 폴더 |
| 고칠 파일 | 한 칸에 한 줄씩 직접 입력(진행률 항목을 고르면 증거 중 코드 파일이 제안으로 채워짐). 데이터·산출물·비밀 경로와 다른 작업이 쓰는 경로는 미리보기가 알려 줌 |

입력할 때마다 부작용 없는 미리보기(`/pair/api/plan`)로 위 값과 검사 결과·겹침 경고를 보여 주고, **준비하고 배정**을 눌러야 폴더·브랜치를 만든다. 고급 설정에서 task ID·기준 SHA·기존 worktree·충돌 그룹을 직접 지정할 수 있다. 도구는 worktree·브랜치를 만들기만 하고 지우지 않는다.

## 작업 계약 (실행의 기준)

목표·완료 조건·허용 파일·작업 테스트·통합 후 검사·실행 환경·상세 지시를 하나의 계약으로 `docs/collaboration/tasks/<task-id>.md`에 렌더링해 **작업 브랜치에만** 커밋한다(main·통합 checkout 거절, 개인 절대경로 미기록). 이 커밋 SHA(`contractSha`)와 내용 해시가 기준이다.

- Git 계약 검사는 계약 커밋 이후 변경만 보고, 계약 파일이 그대로인지 확인한다. 에이전트가 계약을 바꾸면 실패.
- 재시도: 등록 전에 멈춘 준비는 같은 worktree·계약 커밋을 재사용한다. 같은 ID에 다른 내용의 계약이 있으면 거절.
- 실제 CLI 인자에는 계약 경로만 넘긴다(긴 지시는 파일).
- 승인에 계약 해시를 기록하고 통합 직전에 다시 확인한다.
- 작업 테스트 명령은 `{executable: git | node | .venv/bin/python, args[], cwd}`만 받고 셸을 쓰지 않는다. `{base}`·`{contract}`·`{head}` 자리표시자만 치환한다. 학습·실험 기록·자동 교차 검토 진입점은 거절한다.

- 배정 거절: glob·`..`·절대경로, `data/`·`artifacts/`·라벨·비밀 설정 경로, 담당과 다른 브랜치 접두어, `requiresExperiment=true`(학습·모델 비교·사진 추론·라벨 수정·자동 교차 검토는 기본 checkout 단일 담당자 소관).
- 시작 거절: 저장소 worktree 목록에 없는 경로, 기본/통합 checkout, 브랜치 불일치, 기준 SHA가 HEAD의 조상이 아님, Git 진행 중 작업, `.venv` 심볼릭 링크(가상환경 공유), 무료 가드 발동.
- 동시 실행 직렬화: 진행 중(실행·검토 대기·통합 대기 포함) 작업과 허용 파일이 겹치거나, 충돌 그룹(API 계약 등)이 같거나, 공용 설정(`pyproject.toml`, `AGENTS.md` 등 → 암묵 그룹 `shared-config`)을 함께 허용하거나, worktree/브랜치가 같으면 시작하지 않는다.
- 중복 시작: 같은 프로세스 안에서는 동기 구간에서 상태 검사+잠금 획득, 프로세스·재시작을 넘어서는 `task:`/`worktree:`/`branch:` O_EXCL 잠금 파일. 잠금은 종료 확인 또는 사용자의 결과 불명 확정 때만 해제한다.
- `card_condition/`·`tools/experiments/`를 허용한 작업은 해당 worktree의 `./develop -- <CLI>`로 실행해 기존 잠금을 따른다.

## 실행 준비 (worktree 생성 ≠ 실행 가능)

계약 `env`(자동: Python 파일·`card_condition/`·`tests/`·`.venv` 검사가 있으면 python)와 `./develop` 사용 여부로 필요한 환경을 정한다.

| env | 확인 |
|---|---|
| none | 없음 |
| python | 자체 `.venv`(symlink 금지), `pyvenv.cfg`, `.venv/bin/python -I`의 prefix가 이 worktree의 `.venv` |
| python-project | 위 + `-I`로 `card_condition`이 이 worktree에서 import되는지, 필요 모듈 `find_spec` |

미준비면 시작·작업 테스트를 막고 직접 실행할 명령만 보여 준다(가상환경 생성·설치·다운로드 자동 실행 없음). 통합 checkout도 `./develop`용 `.venv`가 없으면 통합하지 않는다.

## 세 가지 검사

| 단계 | 무엇 | 통과 의미 |
|---|---|---|
| 1. Git 계약 검사 | 종료코드·브랜치 HEAD·계약 커밋 위 작업·계약 불변·커밋 존재·미커밋 없음·허용 파일 | 계약 형식을 지켰다. 코드가 맞다는 뜻이 아니다 |
| 2. 작업 테스트 | 사용자가 확인 후 실행기가 감독 프로세스로 계약의 검사를 차례로 실행 | 그 SHA·계약에서 명령이 0으로 끝났다. 미실행·실패·중단·결과 불명·재시작 중단은 통과가 아니다 |
| 3. 통합 후 검사 | 통합 checkout에서 `./develop -- <검사>` | 실패 시 `integrated_check_failed`, 통합 전/후 SHA 기록, 자동 되돌림 없음 |

검사마다 SHA·명령·종료코드·로그·시각을 남긴다. 코드 SHA나 계약이 바뀌면 이전 결과는 "이전 SHA 결과"로 표시되고 승인에 쓰이지 않는다. 서버 재시작 시 끝난 검사의 결과는 기록하지만 남은 검사를 이어서 실행하지 않는다.

## 누구 차례 · 시작 프롬프트 · 메인 인계

- **누구 차례**(사용자/구현 에이전트/메인 에이전트/도구)를 작업 상태에서 파생해 표시한다. 수동 경로의 전환은 사용자가 버튼으로 한다("작업 완료", "메인에게 인계", "메인 확인 완료"). 교대 후 연속 처리는 승인 장부와 무료 조건이 열려 있을 때만 별도 CLI 메인 턴·행동을 진행한다.
- **시작 프롬프트**: 작업 위치(worktree 절대경로)·브랜치·시작 HEAD·기준 SHA·읽을 문서(AGENTS.md, PAIR_CODING.md, 계약, 추가 문서)·목표·완료 조건·허용 파일 수와 목록·검사·진행 방식·금지·인계 형식을 규칙으로 조립한다(LLM 없음). 경로는 복사할 때만 만들고 어떤 파일에도 커밋하지 않는다. `무인 실행` 옵션은 사람 정답 추정·재요청 금지 문구를 추가한다. 추가 문서는 시작 HEAD에 있는 저장소 상대경로만 허용한다.
- **메인 인계**: 커밋이 없거나, 미커밋 변경이 있거나, Git 검사 이후 SHA가 바뀌었으면 거절한다. 인계 문서(전체 SHA와 부모, 변경 파일, 검사·작업 테스트·리뷰 상태, 미검증, 롤백)는 **작업 브랜치에 커밋하지 않고** 상태 폴더에 저장해 복사용으로 보여 준다(PAIR_CODING §4: 완료 후 추가 커밋 금지, SHA 고정). 코드 SHA가 바뀌면 인계는 낡은 것으로 표시되고, 잘못 누른 인계는 승인 전까지 취소할 수 있다. 메인 확인 시각은 승인 기록에 남지만 승인의 필수 조건은 아니다.

## 진행률 항목으로 계약 초안 만들기

`development-progress.json`(통합 브랜치에 커밋된 내용을 `git show`로 읽음)의 **미완료 항목**을 고르면, 완료 조건·현재 평가 원문을 인용한 상세 지시와 목표·완료 조건 초안을 채운다. 증거 파일 중 기준 커밋에 실제 있고 금지 경로가 아닌 코드만 "제안 파일"로 보여 주며 자동 선택하지 않는다. 초안에는 "학습·모델 비교·사진 추론·성능 평가는 기본 checkout의 단일 담당자, 점수·진척률 변경 금지"가 들어간다. 어느 항목을 할지와 허용 파일은 사람이 정한다.

## 독립 리뷰 작업

검토 단계에서 고정 SHA의 계약·diff·검사 결과를 리뷰 묶음(`.state/reviews/<id>/`)으로 만들고, 구현과 **다른 에이전트**의 별도 CLI 프로세스를 그 폴더에서 실행한다. 구현 worktree 경로는 전달하지 않으며, 실행 전후 worktree가 바뀌면 결과를 버린다. 판정은 `approve`·`changes_requested`·`insufficient_evidence`만 인정하고, 형식 오류("통과" 문구 등)·다른 SHA·실패는 판정 없음으로 표시한다. 판정은 승인 기록에 감사용으로 남을 뿐 사람 승인·통합을 대신하지 않는다. 이 화면은 현재 Codex 앱 대화로 메시지를 보내지 않는다. 지금은 fake 리뷰 CLI(`mock/fake-reviewer.mjs`)로만 검증했고 실제 리뷰 CLI는 차단 조건 해결 전까지 거절된다.

## 파이프라인 화면

작업마다 단계 노드 10개를 ArgoCD처럼 한 줄로 보여 준다: 준비 → 구현 → Git 검사 → 작업 테스트 → 리뷰(선택) → 메인 인계 → 사람 승인 → 통합 → 통합 후 검사 → 푸시. 단계 상태(완료·진행 중·할 일·주의·실패·대기·건너뜀)는 작업 상태·검사·인계·승인·통합·푸시 기록에서 화면이 파생할 뿐 저장하지 않는다(`src/ui/js/stages.js`, 단위 검사 `test/ui-stages.test.ts`).

- 위쪽 **지금 단계** 줄: 지금 단계, 차례(누구를 기다리는지), 사람이 누를 대표 버튼 하나.
- 노드를 누르면 그 단계의 설명·담당·상세·버튼이 아래에 열린다. 노드를 누르는 것은 작업 상태를 바꾸지 않는다.
- 왼쪽 작업 카드는 같은 단계를 작은 막대 줄로 보여 준다.
- Mastra 실행 ID·프로세스·계약·로그는 "실행 정보 · 계약 · 로그"에 접어 둔다.

## 허용 파일 범위

허용 파일은 정리된 경로만 받는다: 정확한 파일 또는 `디렉터리/`. `./`·`.`(저장소 전체)·`./docs/`·`a//b`는 작업을 만들 때 거부한다(경로 비교가 글자 그대로의 접두어 비교라서, 정리되지 않은 표기는 금지·충돌 검사를 지나친다). **비워 두면 기본 범위**(코드·테스트·문서: `card_condition/`, `tests/`, `tools/experiments/`, `docs/collaboration/`)가 적용된다. 데이터·라벨·산출물·공용 설정은 기본 범위에 없고 직접 적어도 막힌다. 범위는 실행 중 쓰기를 막는 장치가 아니라 ①병렬 작업의 겹침 감지·직렬화 ②데이터·라벨 보호 ③범위 밖 변경의 사후 표시를 위한 것이다. 두 작업이 같은 폴더를 쓰면 한쪽이 끝날 때까지 기다리므로, 동시에 돌리려면 서로 다른 파일로 좁힌다.

받은 프롬프트에 허용 파일이 적혀 있으면 "3. 어디를 고쳐도 되나요?"의 접힌 칸에서 **가져오기**를 쓴다: 붙여 넣은 글에서 "허용 파일" 목록을 글자 그대로 옮기며(`src/executor/scope.ts`, 언어 모델·추측 없음), 목록이 없으면 아무것도 채우지 않는다. 금지 경로·절대경로·glob·저장소 전체는 사유와 함께 제외한다. 붙여 넣은 글은 저장·커밋하지 않는다.

## 화면 색(밝게·어둡게)

화면 오른쪽 위의 **시스템 / 밝게 / 어둡게** 버튼으로 바꾼다. 기본은 컴퓨터의 라이트/다크 설정을 따르고, 고른 값은 그 브라우저에 기억한다(저장이 막힌 환경에서는 그 화면에서만 적용). 색은 `src/ui/page.html`의 CSS 변수가 정하고 `src/ui/js/theme.js`는 `<html data-theme>`만 바꾼다.

## 단계별 실시간 로그

단계 노드를 누르면 패널 **제목 바로 아래**에 그 단계의 출력이 1초 간격으로 이어서 나온다(로그 단계는 시작 전에도 창이 보이고 안내문이 나온다). 줄은 종류별로 색을 입히고(명령 파랑·오류 빨강·경고 주황·테스트 통과/커밋 결과 초록, 글자 패턴만 보는 표시용) 화면이 받은 시각(HH:MM:SS)을 붙인다. 처음 열 때 이미 있던 줄은 시각이 비어 있다: 구현(에이전트 출력)·작업 테스트(명령별 선택)·리뷰·통합 후 검사. 상태 줄(실행 중/종료·코드·PID·줄 수·경과), 따라가기(스크롤을 올리면 꺼짐), 일시정지, 찾기(일치하는 줄만), 복사. 통합 후 검사는 비밀 패턴을 줄 단위로 가린 뒤 실행 중에 로그 파일에 쓴다(`src/executor/logstream.ts`). 수동 모드는 볼 출력이 없어 작업 폴더 활동(새 커밋·변경·미커밋·범위 밖)을 읽기만 해서 보여 준다. 로그는 CLI가 내보낸 만큼만 보인다.

## 스트리밍 출력과 무과금 가드

실제 CLI는 `claude --print --output-format=stream-json --verbose` / `codex exec --json`으로 실행해 줄 단위 이벤트(JSONL)를 로그에 남긴다(설정 `streamOutput`, 기본 true. `--help`에서 옵션이 확인되지 않으면 텍스트 모드로 돌아가며, `false`로 끌 수 있다). 로그 창은 이벤트를 읽기 쉬운 줄(`$ 명령`, `[도구] 파일`, `→ 결과`, `[완료]`)로 바꿔 보여 주고, 모르는 이벤트와 JSON이 아닌 줄은 원문으로 둔다. 원문 JSON은 로그 파일에 그대로 있고 비용 필드는 화면에 보이지 않는다.

가드(`src/executor/streamGuard.ts`)는 구조화 이벤트에서 **신호 필드만** 검사한다: init의 `apiKeySource`가 API 키 경로(`user`·`project`·`org`·`temporary`)면 서비스 종료·알림, 결제·크레딧 오류 필드와 `is_error` 결과·실패한 턴은 기존 과금·한도 패턴으로 판정(과금 → 서비스 종료·알림, 한도 → 실행 정지). 에이전트가 읽은 파일·쓴 코드 같은 내용 이벤트는 검색하지 않아 "credit balance" 같은 문구가 든 파일을 읽어도 종료되지 않는다. JSON이 아닌 줄은 지금처럼 글 전체를 검사한다. 이벤트 모양은 실제 CLI로 아직 검증되지 않았다(실제 모델 호출은 하지 않음).

## 실행 환경(.venv)

새 worktree에는 `.venv`가 없다(git이 추적하지 않음). 기본 범위처럼 `card_condition/`를 건드리는 작업은 `./develop` 잠금 때문에 자체 `.venv`가 필요하다. 준비 단계의 **환경 만들기** 버튼은 그 작업의 등록된 worktree에서 `python3 -m venv .venv` 하나만 실행한다(셸·패키지 설치·네트워크 없음). 기본 checkout·진행 중 작업·이미 있는 `.venv`는 거부하고, 도구는 `.venv`를 지우거나 다른 checkout의 것을 공유하지 않는다. `pip install -e .` 같은 프로젝트 설치는 여전히 사용자가 직접 한다.

## 되돌리기 · 보관

- **승인 취소**: 승인됨(통합 전) 작업을 같은 SHA로 검토 단계로 되돌린다. 에이전트는 다시 실행하지 않고, 같은 SHA·계약의 작업 테스트 결과는 유효하다. 이전 workflow 실행은 `integrate-gate`에서 `withdraw`로 끝나고 재검토 실행이 이어받는다(`src/executor/taskControl.ts`).
- **보관**: 끝났거나 시작 전인 작업만 목록에서 숨긴다(진행 중·검토·승인 대기 작업은 거부). 기록·worktree·브랜치는 지우지 않으며 "보관된 작업"에서 해제한다.
- 통합 후 되돌리기는 도구가 하지 않는다(reset 없음). 푸시 후에는 푸시 단계의 "되돌림 커밋 준비"를 쓴다.

## 상태 의미

| 화면 표시 | 의미 |
|---|---|
| CLI 실행 중 (workflow `await-exit`) | 실제 프로세스 실행 중. workflow는 종료를 기다릴 뿐 사람 승인 대기가 아니다. **CLI 일시정지는 지원하지 않는다**(중단만). |
| 사람 승인 대기 (`review-gate`/`integrate-gate`) | CLI는 종료됨. 사람이 diff를 열어 본 뒤에만 승인 버튼이 활성화된다. |
| 재시작 전 프로세스 실행 중 | 서버 재시작 후 이전 실행이 살아 있음. 관찰만 하며 재실행하지 않는다. |
| 재시작 후 종료 관찰 · 확인 필요 | 서버가 없는 동안 끝난 실행. 자동 반영하지 않고 "결과 반영"으로만 `await-exit`를 재개한다. |
| 결과 불명 | 감독 프로세스와 종료 기록이 모두 없음. 완료로 보지 않으며 잠금 유지. "결과 불명 확정"은 그룹 종료를 확인한 뒤 잠금만 해제(abandoned). |
| ⚠ 불일치 | 실행기 상태와 Mastra 실행 기록의 기대 관계가 다름. |

중단은 실행기가 만든 감독 프로세스 그룹에만 `SIGTERM`(3초 후 남으면 `SIGKILL`)을 보낸다. 리더 PID는 `ps`의 PGID와 명령행의 spec 경로로 소유를 확인한다(PID 재사용 방지). 다른 세션·서버·에이전트는 대상이 아니다.

## 통합

1. 결과는 전체 HEAD SHA로 고정. Git 계약 검사 통과 + 같은 SHA·계약의 작업 테스트 통과 + diff 확인이 있어야 승인 버튼이 켜진다.
2. 승인 시 SHA·기준 브랜치 HEAD·관련 파일 목록 해시·계약 해시를 기록. 통합 직전 하나라도 바뀌거나 작업 테스트가 승인 SHA와 다르면 승인 무효화(`integration_refused`) → "재검토"(에이전트 재실행 없음).
3. 통합은 `integration` O_EXCL 잠금 + 통합 checkout의 `./develop -- git cherry-pick -x <커밋…>`. checkout이 깨끗하지 않거나 `./develop` 잠금 사용 중이면 승인 유지 후 같은 단계에서 대기.
4. 충돌 시 충돌 파일을 기록하고 `./develop -- git cherry-pick --abort`만 수행. ours/theirs 자동 선택·`reset --hard`·push·force push·브랜치 삭제는 구현하지 않았다.

## 실제 CLI 무과금 조건

실제 CLI 모드는 **구독 로그인으로만** 시작한다(`src/executor/nocharge.ts`, `adapters.ts`). 아래 중 하나라도 있으면 시작하지 않고 원인 코드와 해결 조건을 표시한다. 값은 읽지 않고 이름만 본다.

| 검사 | 근거 |
|---|---|
| API 키·클라우드 토큰 환경변수 | `ANTHROPIC_API_KEY` 등이 있으면 API 요금(Claude Code 문서) |
| Claude 설정의 `apiKeyHelper`, `env`에 API 키 이름, `forceLoginMethod`가 `claudeai`가 아님 | 설정 키 목록은 Claude Code 설정 문서의 색인 기준. 사용자·프로젝트(`.claude/settings(.local).json`) 설정 검사. `forceLoginMethod`의 값 이름은 문서 색인에 없어 보수적으로 차단 |
| 인자의 `--bare`, `--max-budget-usd`, `--betas` | `--bare`는 구독 로그인을 쓰지 않고 API 키를 요구(문서). 문서가 `-p`의 기본값이 bare가 될 예정이라고 해서 CLI 업데이트 때 재확인 필요 |
| `confirmedSubscriptionAuth` ≠ true | Codex ChatGPT 로그인은 `login status`로 별도 확인하지만, 두 CLI의 추가 크레딧 꺼짐·무료 사용 조건 확인을 대신하지 못함 → 사용자가 직접 확인했다는 표시가 필요 |
| `--help`에서 필요한 옵션 미확인 | claude: `--print`, `--permission-mode`, `--allowedTools` / codex: `exec`의 `--cd`, `--sandbox` |

- **Codex 추가 검사**(공식 문서 기준): `~/.codex/config.toml`(또는 `$CODEX_HOME`)의 최상위 `forced_login_method`가 `chatgpt`가 아니거나, `model_provider`가 `openai`가 아니거나, `openai_base_url`이 있으면 차단한다. 그리고 CLI 확인 때 `codex login status`가 "Logged in using ChatGPT"가 아니면(API 키·로그아웃·알 수 없음) 차단한다(`login_not_chatgpt`). 자격 증명 파일은 열지 않는다.
- **인계 + 자동 확인**: 인계 직후 메인 에이전트를 **별도 CLI 프로세스**(`codex exec --sandbox read-only`, 리뷰 묶음만 읽음)로 실행해 approve가 나오면 인계를 자동 확인으로 기록한다(`auto: true`). 대화 중인 메인 세션의 확인이 아니며 승인을 대신하지 않는다. 가드가 막으면 인계만 하고 사유를 알린다. changes_requested/insufficient는 확인하지 않는다.
- **단계 전환 규칙**: 앞 단계가 완료(또는 선택 단계라 건너뜀)된 경우에만 다음 단계가 열린다(화면의 `gate`). 서버의 화면 승인(`approve` API)도 리뷰가 돌고 있지 않고 메인 인계가 확인 완료일 때만 허용한다. 자동 확인이 approve가 아니면(근거 부족·수정 필요·실패) 인계는 확인되지 않은 채 결과(`autoResult`)를 남기고, 사람이 내용을 보고 "메인 확인 완료"나 "인계 취소"를 고른다.
- **메인이 쓴 계약으로 이어 개발하기**: 에이전트 worktree에는 `data/`·`artifacts/`가 없는 것이 원래 설계다(`PAIR_CODING.md` §4, 링크 공유 금지). 그래서 "무엇을 만들지"는 근거를 볼 수 있는 메인이 정해야 한다. 새 작업 폼 2번 단계의 "메인에게 계약 작성 요청 복사"가 (메인이 Codex든 Claude든 같은 형식의) 요청문을 만들고, 메인의 답(`## 목표`·`## 완료 조건`·`## 허용 파일`·`## 읽을 문서`·`## 상세 지시`)을 붙여 넣으면 폼 칸으로 나눈다(규칙 기반, LLM 없음). `읽을 문서`는 계약에 기록되고 시작 프롬프트(자동·수동 모두)에 들어가며, 기준 커밋에 없는 문서는 준비 단계에서 거절한다. 완료 조건과 읽을 문서가 모두 없으면 미리보기가 "보고서만 쓰고 끝날 수 있음"을 경고한다. 시작 프롬프트는 메인(Codex)이 Claude에게 넘길 때 쓰던 형식(작업 식별·먼저 확인할 것·목표와 완료 조건·파일 소유권·구현 제한·검증·진행 방식·산출물과 최종 인계의 8절)을 따르며, 문서·보고서로 끝내지 말고 구현·테스트·커밋까지 하라고 하고, 대상을 정할 근거가 없으면 계약 보완 한 줄만 보고하고 종료하라고 안내한다.
- **메인 역할 교대 실행**(PAIR_CODING §7): 메인 패널의 "새 메인 실행하며 교대"는 ① 새 배정·승인·통합을 멈추고 ② 도구 상태와 실제 Git 헤드로 체크포인트(`.state/main-checkpoints/`)를 저장하며 ③ 새 메인 프로세스(`codex exec --sandbox read-only` 또는 `claude --print --permission-mode plan`, 입력 묶음 폴더만 읽음)를 실행하고 ④ 새 메인이 돌려준 체크포인트 해시·세션 토큰·관찰한 Git 헤드를 도구가 실제 Git과 대조해 일치할 때만 메인과 세대를 바꾸며 ⑤ 승인 장부 범위 안의 행동(`approve_task`·`integrate_task`·`assign_task`)만 기존 기능으로 수행한다. 범위 밖·force push·이력 재작성·세션 묶음 승인은 거부하고, 이전 세대·중복 행동 ID는 무시한다. "교대 완료"는 인수 확인 후 행동이 실제로 수행됐을 때만 표시하며, 행동이 없으면 "인수됨(완료 아님)"이다. 실패(실행 불가·한도·확인 불일치·결과 없음)는 체크포인트를 보존하고 자동 재시도하지 않는다. "한도 소진으로 교대"는 마지막 인계문 없이 저장된 상태로 복구하고 진행 중인 구현 에이전트는 중단하지 않는다. 기존 "표시만 이양"은 새 메인을 실행하지 않는 옛 동작이다. 실제 CLI에서는 확인하지 못했다: 세션 재개·도구 동작, 실제 한도 문구 전체, 잔량 정보(추정하지 않음). mock(fake CLI) 시나리오는 `test/main-rotation.test.ts`.
- Claude 실행은 `--permission-mode acceptEdits`와 `--allowedTools`(Read, Edit, Write, `git status/diff/log/add/commit`)만 쓴다. 그 밖의 Bash는 `-p` 모드에서 자동 거부된다. Codex의 `--sandbox workspace-write` 값은 미검증이다.
- **한도 도달은 정지 신호**다: 한도 문구가 나오면 실행 중인 작업을 멈추고 실제 CLI 시작을 거부하며 서비스는 유지한다. 재시도·크레딧 구매는 하지 않고, 사용자가 풀렸음을 확인해야 해제된다. 한도 안내문에 섞인 "extra usage" 같은 권유 문구는 과금으로 보지 않는다. 반대로 `credit balance` 같은 확실한 과금 문구는 서비스를 종료한다. 한도 문구 목록은 CLI 버전마다 달라질 수 있어 목록에 없는 문구는 일반 실패로 끝난다(자동 재시도·구매는 어느 경우에도 없음).
- 로그인 정보 파일(`auth.json`, 키체인)은 열지 않는다.

## 푸시 · 되돌림

통합된 브랜치를 원격에 올리는 단계다. **푸시는 취소할 수 없으므로** 단계별로 막는다. 실수는 `git revert`로 바로잡는다(force push·`reset --hard` 없음).

1. **점검**(읽기 접속·전송 없음): 통합 checkout 브랜치·깨끗함, `git fetch`, fast-forward 가능 여부, 푸시될 커밋(전체 SHA ← 부모)·변경 파일, 이 범위의 작업 중 통합 후 검사 실패 상태가 있는지, **커밋마다** 금지 경로·5MB 초과 파일·알려진 비밀 패턴(`sk-…`, GitHub 토큰, AWS 키, 개인 키, Slack/Google 키), `git push --dry-run`. 중간 커밋에 들어갔다 지워진 값도 이력에 남으므로 최종 diff가 아니라 커밋별로 본다.
2. **확인 입력**: 대상 SHA 앞 12자를 직접 입력해야 푸시 버튼이 켜지고, 푸시 직전에 다시 점검한다. 점검 이후 로컬이나 원격이 바뀌면 거절한다.
3. **푸시**: 확인한 SHA를 지정한 일반 push(`<sha>:refs/heads/<branch>`), 통합 잠금 안에서 하나만. 실패해도 자동 재시도하지 않는다.
4. **사후 확인**: `ls-remote`로 원격 SHA가 대상과 같은지 확인해 `pushed_verified` / `push_failed` / `push_unverified`(결과 불명) / `remote_mismatch`로 기록한다. "원격 다시 확인"으로 읽기 전용 재확인.
5. **되돌림**: 확인된 푸시에서 "되돌림 커밋 준비"를 누르면 푸시한 커밋마다 revert 커밋을 로컬에 만들고(`./develop` 잠금, 충돌 시 `revert --abort`만), **푸시 전 트리와 같은지** 확인한다. 로컬·원격이 모두 푸시한 SHA 그대로일 때만 가능하다. 그다음 1~4를 그대로 거쳐 올린다. 원래 커밋은 이력에 남는다.

비밀 패턴 오탐(예: 테스트용 가짜 키)은 **커밋·파일·줄 단위로** 사용자가 확인하면 경고로 바뀌고 기록이 남는다. 금지 경로·큰 파일은 확인으로 넘길 수 없다. 이 점검은 알려진 모양만 잡으며 모든 비밀을 보장하지 않는다. 자격 증명은 도구가 다루지 않고 git의 기존 credential helper를 프롬프트 없이 쓴다. 실제 GitHub 푸시는 검증하지 않았다(로컬 bare 원격으로만 검증).

## 메인 역할

"메인"은 통합·푸시·실험의 단일 담당이다. PAIR_CODING.md §7의 메인 역할 교대를 따른다. **새 메인 실행하며 교대**는 체크포인트와 실제 상태를 대조한 인수 확인 뒤 담당·세대를 바꾸고, 이후 행동은 승인 장부·현재 상태·무료 조건을 검사한다. 한도 신호가 있으면 승인 범위 안에서 상대 메인으로 교대하며 잔량을 추정하지 않는다. **표시만 이양**은 새 프로세스를 실행하지 않고 이력·인계 메모만 남기는 수동 기능이며, 사용자가 새 메인에게 메모를 전달해야 한다. 이 수동 기능은 프로세스·통합·푸시·결과 불명 푸시·`./develop` 잠금이 있으면 거절한다. 도구 밖에서 사람이 수행하는 행동까지 강제하지는 않는다.

## 무료 전용 가드

유료 전환 신호가 보이면 서비스(이 실행기의 `mastra dev` 프로세스 그룹과 그 자식 실행)를 종료하고 macOS 알림 + 콘솔 + `.state/alerts/paid-risk.json`으로 알린다. 알림을 `npm run guard:ack`로 확인하기 전에는 다시 시작하지 않는다.

- 시작 시 환경변수 `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `CODEX_API_KEY`, `GEMINI_API_KEY`, `MASTRA_CLOUD_ACCESS_TOKEN` 등(`src/executor/paidSignals.mjs`)이 있으면 시작 거부. 값은 기록하지 않는다.
- 실행 로그에서 확실한 과금 문구(`credit balance`, `insufficient_quota`, `payment required` 등) 또는 권유성 문구(`billing is required`·`billing error` 같은 과금 상태 구절, `extra usage`, `upgrade to …`; `billing` 단독 단어는 코드·지침 예시에도 나와 제외, 공식 오류 문서의 `monthly spend limit`·`usage credits required`는 확실한 과금 문구)를 감지하면 모든 실행을 중단하고 서버를 종료한다. 단 구독 한도 도달 문구와 함께 나온 권유성 문구는 정지로만 처리한다(위 "실제 CLI 무과금 조건").
- 자식 프로세스 환경은 허용 목록(PATH/HOME 등)만 전달하고 위 키를 항상 제거. `MASTRA_TELEMETRY_DISABLED=1`.
- real 모드는 `allowRealModelCalls=true`, `confirmedSubscriptionAuth=true`와 위 무과금 검사를 모두 통과해야 시작.
- `mastra deploy`/`server`/`auth`/`connect` 등 클라우드 명령은 호출하지 않는다.

한계: 실제 청구 여부는 provider 계정에서만 알 수 있다. 이 가드는 신호 기반 차단이며, 신호 없이 과금되는 경로(예: 구독 플랜 자체의 초과 사용 정책)는 감지하지 못한다. `billing` 같은 단어가 정상 코드 출력에 나와도 중단한다(오탐 쪽으로 보수적).

## 보안

`127.0.0.1`에만 바인딩. 모든 요청의 Host는 `127.0.0.1/localhost:<port>`만 허용(DNS rebinding 차단). 상태 변경 요청은 같은 출처 Origin만, `/pair/api/*` POST는 추가로 `X-Pair-Control: 1` 헤더와 Origin이 필수. Mastra Studio의 workflow 실행(`/api/workflows/...`)도 같은 결정적 단계를 거치므로 등록된 task만 시작할 수 있다. Mastra 서버 자체 API(에이전트·도구 등)는 이 도구에서 정의하지 않았다.

## 메인 교대 승인 조건과 행동 결과 (2026-10-29)

- 승인의 `conditions`(자유 문장)는 기계가 검사할 수 없으므로, 문장 조건이 있는 승인은 자동 수행을 **보류**한다(무조건 승인으로 취급하지 않음). 검사하는 조건은 구조화 `requires.handoffConfirmed`(approve_task 단독 승인 전용: 현재 결과 SHA와 일치하는 메인 확인된 인계)뿐이다.
- 새 메인의 행동은 실행 후 작업의 실제 상태로 확인한다. 승인은 `approved`, 통합은 `integrated`+통합 HEAD+필수 통합 후 검사 통과일 때만 성공이며, 차단·거절·충돌·검사 실패는 실패로 기록되어 교대 `completed` 근거가 되지 않는다.
- 응답 구조가 틀리면(예: `actions`가 배열이 아님) 메인·세대를 바꾸지 않고 교대를 실패로 기록한다. 행동은 실행 직전마다 세션·세대·정지 상태를 확인하고 교대와 직렬화되며, 행동 ID는 실행 전에 남겨 중복·결과 불명 재실행을 막는다.
- `node scripts/structure-trace.mjs <시작함수> <파일...>`은 파일별 함수 수와 최장 호출 전이를 정적으로 센다(동적 호출은 이름 일치 후보로 표시).

## 교대 뒤 연속 처리 (2026-10-29, 합성 검증만)

인수가 끝난 뒤(세션이 `completed`/`idle`)부터 기존 300ms 감시 루프가 상태를 읽어(`pipelineTick`, 모델 호출 없음) 다음 단계를 잇는다. 사용자의 복사·재승인은 필요 없지만, 승인 장부에 해당 행동이 **미리 기록돼 있어야** 한다(범위는 넓어지지 않는다).

0. **자동 시작의 승인 범위(2026-10-29 보완)**: "열린 승인"만 자동 단계를 시작시킨다 — 철회 안 됨 + 세션 묶음 일치 + 저장소·브랜치·대상 일치 + **자유 문장 조건(`conditions`)이 없음**. 자유 문장 조건은 기계로 검증할 수 없으므로 사람이 판단하기 전에는 검사·인계·모델 턴을 모두 시작하지 않고(0회) 화면에 보류 사유를 남긴다. 조건을 지우거나 완화해 풀지 않으며, 구조화 조건(`requires`)은 행동 직전에 기계 검사한다. 권한은 섞이지 않는다: ① **준비 권한**(지정 검사·인계 문서)은 `prepare_checks` 또는 `confirm_handoff` 승인이 열려 있을 때만(`approve_task`·`integrate_task` 승인은 준비 권한이 아님 — `handoffConfirmed` 조건 때문에 준비가 필요하면 사용자가 `prepare_checks`를 따로 기록). ② **모델 턴 권한**은 이벤트의 다음 행동(`confirm_handoff`→`approve_task`→`integrate_task`→`push_main`)에 필요한 승인이 열려 있을 때만. `prepare_checks`는 모델이 제안하는 행동이 아니다.
1. **도구 단계(모델 없음, 작업·SHA당 1회)**: 준비 권한이 열린 작업이 `review_pending`이 되면 지정 검사(`runChecks`) → 통과하면 인계 문서 생성. 실패·결과 불명은 재시도하지 않고 `blocked` 이벤트(사용자 판단 필요)로 남긴다.
2. **이벤트 → 메인 턴**: `result_ready`(검사 통과+인계)·`approved`·`integrated`가 새로 생기면 현재 메인에게 읽기 전용 턴을 한 번 준다(같은 이벤트·같은 세대에 두 번째 턴 없음). 입력은 최신 체크포인트·`EVENTS.json`·`diffs/*.diff`·요청문이며, diff 해시는 주지 않는다(메인이 diff 파일을 읽고 직접 계산).
3. **응답은 제안**: 응답 형식·토큰·세션·세대·헤드 대조 후 행동마다 승인 범위·현재 상태·결과를 다시 확인한다. 같은 작업의 앞 행동이 실패하면 뒤 행동은 수행하지 않는다. 같은 행동을 덮는 승인이 여럿이면 기록 순서가 아니라 필수 조건(예: 자기 확인의 `selfReview`)까지 충족하는 승인을 고른다.
4. **행동 종류**: `assign_task`(준비 + 구현 시작; `input.start:false`면 준비만), `confirm_handoff`(현재 SHA·변경 파일 전체·diff 해시·메모 필요), `approve_task`, `integrate_task`, `push_main`(대상=브랜치 이름). 새 행동 `confirm_handoff`/`push_main`은 장부에 명시 기록이 없으면 수행되지 않는다. 구현 에이전트와 같은 에이전트의 확인은 `confirm_handoff` 단독 승인에 `requires.selfReview:true`가 **명시 기록**돼 있을 때만 허용되며(일반 승인으로는 불가), 결과·인계 메모에 "자기 확인(독립 검토 아님)"으로 표시된다.
   **push 범위**: `remoteHead..localHead`의 **모든 커밋**이 통합 승인된 작업의 통합 이력(`integration.preHead..newHead`)에 대응해야 한다. 대응하지 않는 커밋이 하나라도 있으면 자동 push를 하지 않는다(사용자가 수동 push 경로로 직접 확인·push). 이 검사는 `runPush`의 점검·잠금·원격 재확인 직후 같은 계획으로 push 직전에 다시 하며(승인 철회 반영), push는 점검한 계획의 SHA를 명시해 실행한다. 이 도구는 별도 범위 승인을 만들거나 추정하지 않는다.
5. **한도·재시작**: 한도는 **공급자별**이다 — 한도 문구를 낸 실행(메인 세션·구현 worker)의 공급자만 막고(`runtime.limited`), worker면 그 공급자의 실행만 중단한다. 다른 공급자의 교대·실행은 막지 않으며, 같은 공급자는 새 세션·새 worker로도 우회할 수 없다. 출처를 알 수 없거나 공급자 실행이 아닌 출처의 한도는 보수적으로 전역 정지다(과금 신호는 기존대로 전체 정지). 턴이 한도로 끝나면 해당 에이전트를 기록하고 기존 한도 교대로 상대 메인에게 넘긴다(양쪽 한도면 보류 + 체크포인트). 지연·이전 세대 응답은 상태를 바꾸지 못한다.
   **재시작 정책(두 경우를 구분)**: ① *결과 불명 보존* — 서버 재시작 때 끝맺지 못한 턴(시작 중·적용 중·프로세스가 사라진 응답 대기)은 결과 불명으로 보존하고 다시 실행·적용하지 않는다. ② *검증 가능한 저장 응답의 최초 적용* — 재시작 사이에 프로세스가 끝나 종료 기록과 응답이 저장돼 있고 아직 적용 전인 턴은 감시 루프가 종료를 관찰해 같은 검증(세션·세대·토큰·체크포인트·실제 Git·승인)을 통과할 때만 최초 1회 적용한다. 적용이 시작된 턴은 어떤 경우에도 다시 적용하지 않는다. `stop()` 뒤에는 새 검사·턴을 시작하지 않고, 감독 프로세스 시작 실패는 예외 없이 감사 기록(`supervisor_spawn_error`)만 남긴다.
6. **완료 표시**: 화면 요약의 `pipeline`(메인 패널 "교대 후 연속 처리")은 메인 인수 상태·현재 턴, 턴별 개별 행동 결과, 보류·결과 불명 사유, 작업별 `pipelineDone`(검증된 원격 push가 있는 작업만)을 따로 보여 준다.

실제 모델 요청을 동반하는 교대·연속 처리는 검증하지 않았다(가짜 CLI·합성 bare 원격만). 완료한 CLI 메타데이터 검사와 구분하며, 첫 실제 실행 전 계정 무료 조건과 별도 호출 승인을 확인해야 한다.

## CLI 연결 메타데이터 확인 (2026-11-06)

설치된 codex-cli 0.164.0 / Claude Code 2.1.310의 `--version`·`--help`와 Codex `login status`만 대조했다. 필수 옵션·줄 단위 출력 옵션이 확인됐고 Codex는 ChatGPT 로그인 상태를 반환했다. 실제 프롬프트 실행·교대·계정의 추가 크레딧 꺼짐을 검증한 것은 아니다. 운영 설정의 실제 호출 승인·구독 확인 표시는 켜지 않는다.

- `--help`가 실패하면 출력에 옵션 이름이 있어도 확인되지 않은 옵션으로 처리한다.
- Codex 로그인은 종료0과 정확한 ChatGPT 로그인 문장을 함께 확인한다. 설치 CLI가 출력하는 알려진 PATH alias 생성 경고만 분리하고, 다른 문구가 섞이면 미확인으로 둔다.
- 실패·미확인 로그인 원문은 상태/화면에 옮기지 않고 요약만 남긴다. 실제 작업 실행 계획도 같은 로그인 판정을 재검사하므로 화면 확인을 거치지 않은 시작 요청도 API 키 로그인으로 실행되지 않는다.
- 이 확인은 무료 사용·잔여 한도·실제 CLI 쓰기/복구 동작을 보장하지 않는다. 실제 모델 요청 검증은 별도 승인 범위다.

### 실행 직전 무료 조건 재확인 (2026-11-06)

구현 worker는 사전 검사·CLI 탐색·프롬프트 준비 대기가 끝난 직후 `realReadiness`로 실행 승인·구독 확인·환경/설정·한도를 다시 검사한다. 리뷰는 worktree 지문 수집을 먼저 끝내고 같은 검사를 수행하며 중단·과금 가드·메인 동결도 시작 전에 확인한다. 리뷰와 새 메인은 실제 입력 묶음 폴더의 Claude 설정도 검사한다. 해석하지 못하는 Codex 전역 `profile` 선택은 무료로 간주하지 않고 차단한다.

이 보완은 fake CLI의 상태 변경 반례로 검증한다. 실제 모델 요청·계정의 추가 크레딧 꺼짐 검증은 하지 않았으며 운영 실제 호출/구독 확인 설정은 변경하지 않는다.

### 준비 대기 뒤 메인·승인·대상 상태 재확인 (2026-11-06)

메인 턴은 체크포인트·CLI 탐색이 끝난 직후 세션·세대·동결·중단과 이벤트의 현재 작업 상태/SHA·시작 승인을 다시 검사한다. 준비 중 메인이 바뀌면 이전 턴은 stale로 남긴다. 승인이나 대상이 바뀌면 전송 전 입력 묶음을 취소하고 해당 이벤트만 보류한다. 아직 모델 요청을 보내지 않은 독립 이벤트는 최신 입력으로 최초 실행할 수 있다. 실제 시작 기록이 있거나 결과 불명인 요청을 재시도하는 것은 아니다.

자동 작업 테스트·인계 문서 생성도 같은 메인 맥락을 전달하고 Git 준비 대기 뒤 저장 직전에 기존 준비 승인 범위를 재검사한다. 수동 요청은 별도 자동 준비 승인을 요구하지 않는다. 중단·과금 가드 뒤에는 새 검사 등록·대기 검사 시작을 차단하며, 감시 루프도 새 교대를 진행하지 않고 기존 실행의 종료 관찰은 유지한다.

### API 최종 변경 경계 재검증 (2026-11-07)

배정·worktree 생성·작업 승인·인계 확인·통합은 마지막 Git 준비 대기 뒤 중단·무료 가드·동결·메인 세대를 다시 확인한다. 자동 행동의 세션·수명·승인 범위도 서비스까지 전달해 기존 approvalGate에서 다시 검사한다. 승인과 인계 확인·통합은 현재 작업/검사/계약 상태를 대조한다. 표시 메인 변경은 준비 중 세대나 표시가 바뀌면 거부한다.

계약 파일은 배타적으로 생성해 준비 중 생긴 다른 파일을 덮어쓰지 않는다. 계약 커밋 뒤 등록이 막히면 커밋을 보존하고, 사람이 같은 계약으로 다시 배정할 때 기존 커밋을 재사용한다. 이미 시작한 통합은 임의 취소·자동 재실행하지 않으며 stop/무료 가드 뒤에는 남은 통합 후 검사를 새로 시작하지 않고 미실행으로 기록한다. 이 변경은 임시 Git·가짜 CLI 회귀로 검증하며 새 실제 모델 요청은 실행하지 않는다.
